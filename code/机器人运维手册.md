## 五、改回复频率

编辑 `/home/qqbot/qq-bot/.env`：

| 参数 | 默认 | 含义 |
|---|---|---|
| `MIN_REPLY_INTERVAL` | 40 | 同群两次回复的最小间隔（秒），防刷屏 |
| `PROB_QUESTION` | 0.85 | 问句结尾时的回复概率 |
| `PROB_MATH_WORD` | 0.45 | 出现数学关键词时的回复概率 |
| `PROB_IDLE` | 0.03 | 纯闲聊插嘴概率 |
| `DROP_PROB` | 0.08 | 非 @ 消息「装没看见」的概率 |
| `TYPING_PER_CHAR` | 0.055 | 每个字"打字"耗时，调大=回得更慢更自然 |
| `MAX_PARTS` | 3 | 一条回答最多拆成几段发 |

改完 `systemctl restart qqbot`。

> 被 @ 和被叫「阶导」时**永远必回**，这个不受上面参数影响。

### 「@ 必回」是怎么保证的

不是只把概率设成 1.0 就完事——那条路有三个漏口，都单独堵上了：

| 漏口 | 堵法 |
|---|---|
| 同群冷却会把点名的消息吞掉（阶段1 间隔长达 120 秒） | 被 @ 时**绕过冷却**，只受 `MENTION_MIN_INTERVAL` 约束（默认 0 = 完全不限） |
| 模型可以自己选 `ignore`，点名了也不理 | prompt 里对点名消息下硬指令：action 只能是 reply |
| 模型坚持不接（问题太模糊/没法答） | **兜底回应**：随机发一句「在的，你说」「嗯？我在」「怎么了？」「在，说吧」，绝不冷场 |

已验证的场景：

- 同一秒内 3 个人同时 @ → 3 条全部回应，一条不漏
- 刚回完 0 秒间隔又被 @ → 照常回应
- 强制模型返回 ignore + 消息 @ 了它 → 兜底回应生效
- 对照：冷却期内的**非 @** 闲聊 → 正常跳过，不会刷屏

`MENTION_MIN_INTERVAL` 是唯一的例外开关。默认 0（无条件必回）；**万一将来有人刷屏式 @**，
把它调成 5～10 秒就能限流，代价是这期间的点名可能被漏掉。

## 五之二、逐步融入群聊的时间表 ⭐

新号一进群就什么话都接、还主动搭话，是最容易被看出是机器人的。而且参考文档里的教训：
**未信任设备 + 高频活动 = 加速风控**。所以做了个「越来越放得开」的时间表。

**它不是定时任务，而是按"已经过多久"实时算出来的。** 这样比 cron 更可靠：不依赖任务有没有
按时跑、机器重启也不影响进度、也不会因为漏跑一次就卡在某个阶段。

| 阶段 | 进入时间 | 主动插嘴 | 数学词回复 | 问句回复 | 同群间隔 | 装没看见 |
|---|---|---|---|---|---|---|
| 阶段1 | 现在～3 小时后 | **0%**（纯潜水） | 15% | 50% | 120 秒 | 30% |
| 阶段2 | 3 小时后 | 2% | 30% | 70% | 90 秒 | 20% |
| 阶段3 | 6 小时后 | 5% | 45% | 85% | 60 秒 | 12% |
| 阶段4 | 24 小时后 | 8% | 50% | 85% | 40 秒 | 8% |

**凌晨静默**：凌晨 1:00–7:00 之间**不主动搭话**（插嘴概率归零），但被 @ 和要 PDF 照常回。
一个真人不会凌晨四点在群里主动找话题，这是最容易露馅的细节。

### 查现在处于哪个阶段

```bash
sudo -u qqbot /home/qqbot/qq-bot/venv/bin/python /home/qqbot/qq-bot/rampup.py
```

输出会告诉你：起始时间、已过多少小时、当前阶段、下一阶段几点进入、各项当前参数。

### 想调整

编辑 `/home/qqbot/qq-bot/rampup.py` 里的 `PHASES` 表，然后 `systemctl restart qqbot`。

- 想**立刻变成活跃状态**：把第一项的 `idle` 改成 `0.08`、`interval` 改成 `40`
- 想**从头再慢一次**：删掉 `/home/qqbot/qq-bot/state/rampup.json` 再重启
- 嫌它**太活跃/太安静**：直接改 `idle`（主动插嘴）和 `drop`（装没看见）

起始时间存在 `state/rampup.json`，重启服务**不会**重置进度。

## ⚠️ 素材处理的两条硬规矩（车主 2026-10-10 定）

### 规矩 1：**默认不压缩、不处理，原样存**

> **车主说了才处理，不说就直接原样存进去。**

加素材时的默认动作就是**复制**，一个字节都不要动：

```bash
cp "来源.mp4" "$BOT/stickers/videos/video_XX.mp4"

# 存完一定要校验，确认真的没被改动
md5 -q "来源.mp4"                                    # 本机
ssh root@服务器 "md5sum /home/qqbot/qq-bot/stickers/videos/video_XX.mp4"
# ↑ 两个值必须一模一样
```

**只有车主明确说"压缩"、"加速"、"2 倍速"这类要求时，才去动文件。**
下面的 ffmpeg 配方是**只在被要求时才用**的工具箱，不是默认流程。

> 为什么定这条：压缩是有损的，而且改过的版本**没法还原**。
> 原片留着就留着，真要处理随时能做；反过来，压过头就再也回不去了。
> （另外实测过：随手压一压，体积反而可能从 1.8MB 涨到 2.6MB —— 参数不对是白忙。）

### 规矩 2：**手动发过素材之后，必须校正游标**

**这个坑踩过一次**：手动调用 `onebot.send_group_video()` 直接发视频，
**不会推进 `state/media_cursor.json`** —— 因为只有 `media.pick()` 才会写游标。

**后果**：游标还停在老位置，机器人下次自动想发视频时，**可能立刻重发刚发过的那条**。

**修法**（发完手动校正）：

```bash
sudo -u qqbot /home/qqbot/qq-bot/venv/bin/python - <<'PY'
import json, pathlib, sys
sys.path.insert(0, '/home/qqbot/qq-bot')
import media

f = pathlib.Path("/home/qqbot/qq-bot/state/media_cursor.json")
cur = json.loads(f.read_text(encoding="utf-8"))
pool = sorted(p.name for p in media.list_videos())     # 或 list_images()

# video_idx 指向「下一次该发的那条」= 不是刚发过的那条
just_sent = "video_02.mp4"                              # ← 改成你刚手动发的
cur["video_idx"] = (pool.index(just_sent) + 1) % len(pool)
cur["video_last"] = just_sent                            # 记录真实最后发送的
f.write_text(json.dumps(cur, ensure_ascii=False), encoding="utf-8")
print("下次会发:", pool[cur["video_idx"]])
PY
chown qqbot:qqbot /home/qqbot/qq-bot/state/media_cursor.json
```

**⚠️ 还有一个隐蔽的坑**：**光是"模拟 pick"就会推进游标**。
调试时如果想试"下次会挑到哪条"，**别直接调 `media.pick()`** ——
它会真的写盘。要看就直接按规则算：`pool[cursor['video_idx']]`。

### 视频处理配方（本机 ffmpeg 加速 / 压缩）

> 🚫 **只在车主明确要求时才用这一节。** 默认是规矩 1：原样存。

> ⚠️ **本机有 ffmpeg，但不在 PATH 里**，必须写全路径：**`/opt/homebrew/bin/ffmpeg`**
> （`brew` 命令本身找不到，但二进制装着 —— 这是踩过的坑，别以为没装）

**2 倍速**（原片 18 秒 → 9 秒）：

```bash
FF=/opt/homebrew/bin/ffmpeg
$FF -y -i "输入.mp4" \
  -filter_complex "[0:v]setpts=0.5*PTS,scale=1280:-2[v];[0:a]atempo=2.0[a]" \
  -map "[v]" -map "[a]" \
  -c:v libx264 -preset medium -crf 25 -pix_fmt yuv420p \
  -c:a aac -b:a 96k -movflags +faststart \
  "输出.mp4"
```

几个参数为什么要这么写：

| 参数 | 为什么 |
|---|---|
| `setpts=0.5*PTS` | 视频时间戳压一半 = 2 倍速。想要 1.5 倍就写 `0.667*PTS` |
| `atempo=2.0` | 音频同步加速，**保持音调不变**（不会变尖）。单次最大 2.0，要更快得串联 |
| `scale=1280:-2` | 压到 720p。**群聊视频没必要 1080p** —— 手机上没区别，但发送慢一倍 |
| `-crf 25` | 质量/体积平衡点。实测 1080p+crf23 会到 2.6MB，720p+crf25 只有 1.3MB |
| `-movflags +faststart` | 把索引放文件头，群里可以边下边播 |

**先看视频内容再发**（121 人的群，别盲发）：

```bash
$FF -y -v error -ss 1 -i 输出.mp4 -frames:v 1 -vf scale=560:-2 /tmp/f1.png
# 再抽 4s、7s 各一张，拼起来看
```

> ⚠️ ffmpeg 9.0 **删掉了 `-vsync`**（换成 `-fps_mode`），老教程里的写法会直接报错。
> 用 `-ss <秒> -frames:v 1` 逐帧抽取更稳。

### 怎么发的

- **轮流发，不重样**：游标存在 `state/media_cursor.json`

> 🚫 **素材一律等权重，不要给任何一个加权**（车主 2026-10-10 明确要求）。

## 六、故障排查

### 群里 @ 它没反应

按顺序查：

```bash
# 1. 答疑进程活着吗
systemctl is-active qqbot

# 2. QQ 还登录着吗（返回 QQ 号才算正常）
TOKEN=$(cat /home/qqbot/napcat_token)
curl -s -X POST http://127.0.0.1:3000/get_login_info \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{}'

# 3. NapCat 进程在吗
pgrep -af '/opt/QQ/qq'

# 4. 日志里看到你那条消息了吗
tail -30 /home/qqbot/qq-bot/bot.log
```

- **1 挂** → `systemctl start qqbot`
- **3 挂** → NapCat 死了，见下一节
- **都正常但日志里没那条消息** → 检查是不是发在别的群（只服务 <群号>）
- **日志里有「模型选择不接话」** → 正常克制行为，不是故障。想让它更爱接话就调 `PROB_*`

### 被踢下线（KickedOffLine）

1. **先等 2–3 分钟**，看会不会自动重连，不要急着重启
2. 确认没有第二个实例在抢号：`pgrep -af '/opt/QQ/qq'` 只应有一个
3. 还在循环掉线 → 手机 QQ → 设置 → 账号安全 → **登录设备管理**，删掉旧设备记录，只留手机和服务器
4. **手机 QQ 保持在线**（桌面端会话依附手机端）
5. 连续被踢 3 次以上，停 30 分钟~1 小时再试，让风控冷却

### 回复里没有公式图片

多半是渲染失败，看日志里的「渲染失败」：

```bash
grep -i '渲染失败' /home/qqbot/qq-bot/bot.log | tail -5
```

常见原因：模型给的 LaTeX 语法错误。这类问题不会让机器人崩，只是那条图片发不出来。想复现具体式子：

```bash
cd /home/qqbot/qq-bot/latex
sudo -u qqbot /home/qqbot/qq-bot/venv/bin/python render.py \
  --mode card --body '\[ a^2+b^2=c^2 \]' --out /tmp --name probe
```

## 七、服务器重启后怎么办 ⚠️

这是**唯一需要人工介入**的场景。

1. systemd 会自动拉起 NapCat（环境变量已修好，不会再崩）
2. 但 NapCat 大概率会停在**扫码界面**（quick login 实测不可靠）
3. 二维码在 `/home/qqbot/Napcat/napcat/cache/qrcode.png`，**1–2 分钟过期**，且会自动刷新
4. 把这个文件取出来扫码即可

```bash
# 重启后确认状态
systemctl is-active napcat qqbot
tail -20 /tmp/manual_napcat.log        # 或 journalctl -u napcat -n 30
stat -c '%y' /home/qqbot/Napcat/napcat/cache/qrcode.png
```

如果重启后 NapCat 是被 systemd 拉起的（不是手工），日志在 `journalctl -u napcat` 和 `/home/qqbot/napcat.service.log`。

## 九、安全说明

已经做的：

- SSH **禁用了密码登录**，只认密钥；root 也是 key-only
- `fail2ban` 自动封爆破 IP；`ufw` 只放通 22

## 十之二、额度监控 💰

### 先搞清楚：什么在花钱，什么不花

这是最容易搞混的地方。**机器人发消息多少，和这 ¥300 额度基本无关。**

| 你干的事 | 消耗什么 | 属于哪个钱包 |
|---|---|---|
| **服务器开着**（不管机器人跑不跑） | ¥0.254 / 小时 | ⬅️ **就是这 ¥300 额度** |
| 群里聊得多、答得多 | DeepSeek 的 token | 另一个钱包（平台送的 API 额度） |
| 发图片、表情包、PDF | 公网流量 | 阿里云**另有 20 GB 免费额度**，我们才用了 0.001 GB |

**两个关键结论：**

1. **关掉机器人省不了这 ¥0.254/小时** —— 只要实例还开着就在扣。想省钱只能**停机**或**释放实例**
2. **聊天多只多花 DeepSeek 的钱**，跟阿里云这 ¥300 没关系（流量有独立免费额度，表情包一张 30KB，发 1000 张才 30MB）

### 两条防线，都要有

有两条独立的防线，**两条都要有**。

### 防线一：阿里云自带的「可用额度预警」（权威，必须设）

这是**免费**的，也是唯一准确的一条。余额低于你设的阈值，它会发**短信 + 邮件**。

> 控制台 → **费用中心** → 左侧「**可用额度预警**」→ 打开 → 阈值填 **100**
> （意思：余额低于 ¥100 就通知你。你有 ¥300 额度，相当于花了 ¥200 就提醒）

顺便建议再把「**账单提醒**」也打开，可以设每日/每周推账单。

### 防线二：服务器本地的估算 + QQ 推送（趋势预警）

`spend.py` 每 5 分钟跑一次（挂在 `healthcheck.sh` 里），估算这台机器的累计消费：

```
运行小时数 × 每小时单价  +  累计出站流量 × 每 GB 单价
```

累计到 **¥200** 就**通过 QQ 私聊发给你**（发到 `SPEND_ALERT_QQ`，默认你的主号）。只提醒一次，不会刷屏。

看当前估算：

```bash
sudo -u qqbot /home/qqbot/qq-bot/venv/bin/python /home/qqbot/qq-bot/spend.py
```

输出形如：

```
[额度估算] 运行 2.9h × ¥0.2 = ¥0.57  |  流量 0.00GB × ¥0.8 = ¥0.00  |  合计 ¥0.57
```

状态存在 `state/spend.json`，计费起点取系统开机时间（新实例≈创建时间）。

### ⚠️ 估算的局限，必须知道

1. **它不是账单**，是两个单价乘出来的估算
2. **单价已按实测校准**：`SPEND_HOUR_RATE=0.254`（元/小时）。
   这个数字是 2026-10-10 从阿里云试用额度页读到的真实扣费速率——
   页面上写的是「ECS实例及系统盘 · 已用额度 0.254元/小时」。
   以后阿里云如果调价、或者你换了配置，去那个页面重新读一下，改这个数字即可
3. **实例如果被停止过再开机**，估算会偏小（停机时段不计费，但这里按连续运行算）
4. **它没法知道你有多少免费额度**，只算"用了多少"

所以：**防线一负责准，防线二负责早。** 缺一个都不行。

## 🚫 新增线路的规矩（车主 2026-10-10 定，长期有效）

> **末尾两个位置是「备选的备选」，永远不动：**
> **倒数第一 = 中转站，倒数第二 = 火山方舟。**
>
> **以后再加模型，默认插在这两个前面 —— 也就是「倒数第三位」。**
> 插进去之后，后面的线路依次顺延。

**为什么这么定**：方舟和中转站都是**"实在没别的了才用"**的兜底
（中转站免费但慢，方舟是第三方且额度有限）。
新接的线路正常情况下都比它们可靠，理应排在它们前面。

```
      ┌─── 主线路 / 备用1 / 备用2 ………… 按可靠性排
      │
      ├─── ★ 新线路默认插这里（倒数第三）
      │
      ├─── 火山方舟     ← 备选的备选，位置固定
      └─── 中转站       ← 永远最后一个
```

**操作步骤**（可以照着抄）：

1. `.env` 里加一组 `FALLBACKn_*`，把原来的方舟/中转站**往后挪一位**的编号
   （比如方舟从 `FALLBACK4_*` 变 `FALLBACK5_*`，中转站从 `FALLBACK5_*` 变 `FALLBACK6_*`）
2. `config.py` 的 `_build_providers()` 里，在方舟那条 `add()` **之前**插入新的 `add()`
3. 重启，跑一遍逐级降级验证
4. **顺手改这里的表格和说明**（`/tmp` 里那套降级测试脚本可以重建）

> ⚠️ **注意编号会随插入顺延**，所以 `.env` 里的 `FALLBACKn` 前缀**不代表"第几条"**，
> 只代表"配了一组"。真正的顺序由 `config.py` 里 `add()` 的先后决定 ——
> 改顺序时两边都要动，只改一边会出现"编号和位置对不上"的混乱。

---

**这个顺序让「赠送额度过期」变成逐级降级，而不是突然哑掉**：

```
现在 ~ 10-13    走主线路（官方A）
10-13 ~ 10-17   自动降到备用1（官方B）
10-17 之后       备用3（官方C）→ 备用4（小米）→ 备用5（方舟）→ 备用6（中转站）
```

配置在 `.env` 里，依次用 `DEEPSEEK_*` / `FALLBACK_*` / `FALLBACK2_*` /
`FALLBACK3_*` ~ `FALLBACK8_*` 前缀，`*_NOTE` 是纯备注（写到期时间很方便）。

⚠️ **官方 key 的余额是「账号级」的，不是「key 级」的。**
如果同一个账号下还有别的 key 在别处使用（比如你自己别的项目），
它们会**一起消耗这个余额** —— 所以某条线路可能比预期更早见底。
这不是异常，看余额掉得快先确认是不是自己在别处用了。

代码在 `brain.py` 的 `decide()`：按顺序试每条线路，只有 HTTP 200 才用它；
网络错误、HTTP 错误、返回结构异常、以及**输出被 max_tokens 截断**，
都会自动跳下一条（截断会直接停，因为换线路也会同样截断，没必要白烧调用）。

### 🔍 两个推理模型的对比（别照搬处理方式）

小米 MiMo 和火山方舟**都是推理模型**，但行为完全不同，**处理方式正好相反**：

| | 小米 MiMo 2.6 Flash | 火山方舟 deepseek-v4-1-flash |
|---|---|---|
| 思考用量 | **会自己判断**（解积分只用 7 token）| **不管需不需要都想**（识图用 269~315）|
| 要不要关 | ❌ **不要关** | ✅ **必须关** |
| 关掉的后果 | 反而更慢（13.5s vs 9.4s）| 才能正常返回正文 |
| 多模态质量 | 开着思考能认出角色出处 | 关掉质量不变 |

**判断方法**：发一个简单请求，看 `usage.completion_tokens_details.reasoning_tokens`。

- 接近 0 → 它自己会省，**别管它**
- 和 `completion_tokens` 差不多 → 它在无脑思考，**必须关**

> 💡 **换模型时别照抄上一条的 `extra` 参数** —— 每条线路的思考行为都可能不同，
> 一定要实测一次再决定。

### ⚠️ 火山方舟（备用5）的专属坑：**必须关掉「思考」**

方舟的 `deepseek-v4-1-flash-260910` 是**推理模型**：先输出 reasoning 再输出正文，
而 **reasoning 也算进 `max_tokens`**。实测：

```
max_tokens=50  → reasoning 吃掉 50，正文返回【空字符串】   ← 灾难
max_tokens=100 → reasoning=38，正文 11 字，正常
max_tokens=2000→ reasoning=15，正常
```

**空正文会让 JSON 解析直接失败**，整条线路作废。

**解法**：在 `config.py` 里给这条线路加了专属参数：

```python
extra={"thinking": {"type": "disabled"}}
```

`brain.py` 会把它并进请求 payload。关掉思考后：

| | 开着思考 | 关掉思考 |
|---|---|---|
| 耗时 | 3.1s | **1.3s**（快 2.4 倍）|
| reasoning tokens | 269 | **0** |
| 正文 | 正常（但要留足 max_tokens）| 正常 |
| 识图质量 | 好 | 一样好 |

> 💡 **换方舟其他模型时要注意**：如果换成别的推理模型，
> 这个 `thinking` 开关可能名字不一样，或者不需要。
> 判断方法：看 `usage.completion_tokens_details.reasoning_tokens` 是不是 0。

### ⚠️ 踩过的坑：**增删线路时，备注容易跟着编号串位**

同一个坑的第二副面孔。给 `add()` 块重新编号时，**`FALLBACKn_NOTE` 这类变量名很容易改串**：

```python
add("备用3", ..., os.environ.get("FALLBACK4_NOTE", ...))   # 🔴 读了隔壁的备注
add("备用4", ..., os.environ.get("FALLBACK3_NOTE", ...))   # 🔴
```

结果就是**地址和模型是对的，只有显示用的备注串了位**——不影响功能，但看的人会被带偏。

**怎么防**：改完跑一遍逐块核对（按 `add("xxx", ...)` 切块，检查每块用到的
`FALLBACKn_*` 前缀是否唯一且与该块编号一致）。项目里已经这么测过了。

> 💡 根因还是同一个：**位置（编号）和身份（服务）被绑在一起了。**
> 真正的解法是让备注也**按接口地址走**，而不是按编号 —— 但 `config.py` 里必须显式写变量名，
> 所以只能靠"改完必查"来兜。

### ⚠️ 踩过的坑：**按编号硬编码会错位**

增删线路时，后面所有「备用N」的编号都会挪位。**任何按编号写死的映射都会失效。**

真实踩过：`show_api_lines.py` 里额度标注是按 `"备用4": "¥10"` 这样写死的，
撤掉官方D 之后编号一挪，显示变成：

```
备用3（小米）  →  显示 "10-17 到期"   ← 错，那是原官方D的
备用4（方舟）  →  显示 "¥10"          ← 错，那是小米的
备用5（中转站）→  显示 "50 万 token"   ← 错，那是方舟的
```

**修法**：改成**按接口地址判定**，怎么挪位都不会错：

```python
BY_HOST = {
    "xiaomimimo.com":  ("¥10",         "40 天后到期，多模态"),
    "ark.cn-beijing":  ("50 万 token", "推理模型，已关思考"),
    "bingheai.org":    ("会员免费",     "中转站，慢，最后兜底"),
}
hit = next((v for k, v in BY_HOST.items() if k in p["base_url"]), None)
```

> 💡 **通用原则**：**能按"身份"判定就别按"位置"判定。**
> 位置会变（增删、排序），身份不会（接口地址、模型名是这个线路的固有属性）。

替代方案：`apiwatch.py` 会探活最后一条线路，**所有线路同时失效时每 6 小时 QQ 告警你一次**。

### 想换模型 / 加第六条线路

换模型：改对应的 `*_MODEL`（中转站支持的模型用 `probe_relay.py` 列出来）。

加线路：在 `.env` 里加 `FALLBACK5_*` 那组，再在 `config.py` 的
`_build_providers()` 里照抄一段 `add()` 即可。**记得中转站永远留在最后一条。**

### 当前的闲聊强度（2026-10-10 车主定的）

车主的要求是：**像群里另一个机器人 muse 那样参与闲聊，但不用那么频繁，有它 50%~75% 就够。**

```
muse 实测              9.4 条/小时
目标区间               4.7 ~ 7.1 条/小时
当前标定               6.1 条/小时   ✅
```

**这些数字是用群里真实消息标定的，不是拍脑袋**：

```
实测 126 条真人消息样本：
  人类消息密度     40.2 条/小时
  问句             3%      ← 一开始我以为 15%
  含数学词         0%      ← 我以为 30%，完全错了
  纯闲聊          97%

→ 结论：这个群现在几乎全在闲聊，math 规则现实中根本不触发，
        **实际全靠 idle 在决定频率**，所以 idle 标到了 0.13。
```

> ⚠️ **调频率要改 `MAX_CHAT_PER_HOUR`，别改 `idle`！**
>
> 这是实测出来的反直觉结论。群里消息密度 50.7 条/小时、而且是**爆发式**的，
> 所以真正在限流的是那个**滚动 1 小时的硬上限**，不是概率。
> 实测（每个值跑 30 遍取平均）：
>
> ```
> idle      实际频率       说明
> 0.08      6.3 条/小时
> 0.13      6.8 条/小时   ← 当前
> 0.20      7.3 条/小时
> 0.25      7.9 条/小时
> ```
>
> **idle 从 0.08 调到 0.25（3 倍），频率只从 6.3 涨到 7.9（25%）。**
> 因为爆发时很快就撞到小时上限被截断了。
>
> 所以：**想要更安静就调低 `MAX_CHAT_PER_HOUR`；调 idle 几乎没用。**
> 参考换算式（粗算）：`条/小时 ≈ min(idle × 群消息密度 × 0.6, MAX_CHAT_PER_HOUR × 0.7)`
>
> ❌ 早先文档里写过 `条/小时 ≈ idle × 40`，那个是错的 —— 它漏算了
> 「跟别人说话」这一层过滤（群里 36% 的消息是在 @ 别人），也没算硬上限的截断。

⚠️ **`IGNORE_NAMES` 里的机器人名字不要删** —— 那是防止两个机器人互相接话
**死循环**的保险。muse 和凛音同学说的话，我们一律不接。

实现上分两层，别混：

- **触发层**（`main.should_reply`）：只有 `mentioned` 能触发；`MENTION_ONLY` 保证没点名的一律不接
- **素材层**（`vision.extract`）：被 @ 之后才去回溯引用消息、把图取出来送给模型

⚠️ 别在触发层加"看到图就回""问句就回"的规则。已经踩过两次坑，见「十五、踩坑记录」。

### 曾经的一个大坑（已修）

早期版本的 `onebot.message_text()` 为了省事，把图片段**直接替换成 `[图片]` 三个字**——
模型收到的永远只有这三个字，压根没有图。表现就是：群友发图让它批改，
它答非所问或者自称"看不到图片"。**API 一直是支持的，是代码把图丢了。**

### 现在怎么做的

`vision.py` 负责取图，流程是：

1. 从消息段里找出 `image` 类型的段
2. **遇到 `reply` 段（引用），用 `get_msg` 回溯被引用的那条消息**，把里面的图和文字一起取出来
   （群友的典型操作就是"发图 → 引用图 → @ 机器人"，光看当前消息是拿不到图的）
3. 下载图片 → 压到长边 1024px → base64 成 data-url
4. 以多模态格式塞进请求：`content: [{"type":"text"...}, {"type":"image_url"...}]`

### ⚠️ 为什么不走 NapCat 给的本地路径

`get_image` 返回的本地文件在 `/root/.config/QQ/...` 下，而 `/root` 权限是 **700**、
文件是 **600**，机器人跑在 `qqbot` 用户下**读不到**。

所以走它同时返回的 **CDN url**（`multimedia.nt.qq.com.cn/download?...&rkey=...`），
实测无需额外鉴权，直接能下。注意 `rkey` 有时效，所以必须**收到消息就立刻下载**，
不能排队等。

### 成本控制

图片非常吃 token，所以有三道闸：

| 闸 | 值 | 原因 |
|---|---|---|
| 单条消息最多几张图 | 3 张 | 防 token 爆炸 |
| 图片长边上限 | 1024 px | 超过先缩（需要 Pillow） |
| 单张体积上限 | 12 MB | 超过直接放弃 |

另外 **QQ 自带表情（`sub_type == 7`，或 summary 形如 `[发怒]`）会被跳过**——
那是表情包不是内容，占一个视觉名额不值。

### 实测效果

拿一张**故意写错符号**的分部积分图测（最后一步应是 `x·eˣ − eˣ + C`，图上写成了 `+ eˣ`）：

> 思路完全正确……**结论：最后一行符号错了。你写的是 $x e^{x} + e^{x} + C$，
> 但前面那个减号要一直带下来，应该凑成 $-e^{x}$，不是 $+e^{x}$。**
>
> 验算一下更保险：对 $x e^{x} - e^{x}$ 求导，得 $(e^{x} + x e^{x}) - e^{x} = x e^{x}$，
> 和原被积函数一致，说明答案正确。而你的答案求导会多出 $2e^{x}$，显然不对。
>
> 总评：方法全对，只栽在最后一步的符号上，可惜。

它不但认出来了，还**自己求导验算了一遍**来证明错在哪。

### ⚠️ 注意：识图会让 API 消耗明显变快

一张 1024px 的图大约 1000–1500 token，和整段提示词差不多量级。
**有图的那次请求，输入 token 大概是纯文字的 2–3 倍。**

主线路余额本来就只剩几块钱，如果群里发图求批改变多，消耗会明显加快。
这不是 bug，是图片的固有成本。要控的话调 `vision.py` 顶部的 `MAX_LONG_SIDE`（数字调小更省）。

**所以定了个原则：框只用来框「输入」（题目/定理），不框「输出」（解答）。**

## 十四、PDF 文件名 与 收尾 @ 通知

两个「像人」的细节，都写在 `persona.py` 的 `OUTPUT_RULES` 里，由模型决定内容。

### 1. PDF 文件名按任务类型起，不是固定一个名字

模型输出 `math` 片段时会带一个 `filename` 字段（**不带 `.pdf`**，程序自己加）：

| 场景 | 文件名 |
|---|---|
| 批改别人的解题过程 | `批改过程` |
| 一步步解一道题 | `解题过程` |
| 推导公式/定理 | `推导过程` |
| 对比几种解法 | `解法对比` |

**禁止**用「文档」「报告」「output」这类没信息量的名字，也禁止每次都叫同一个。

文件名在 `brain._safe_filename()` 里做了清洗：挡掉 `\ / : * ? " < > |` 和控制字符
（这些会破坏 QQ 文件上传，甚至被当成路径分隔符），限长 40 字，自动去掉模型误加的 `.pdf`。

兜底：模型没给名字时用「解答过程.pdf」。

### 2. 发完文件后，单独 @ 提问者说一句话

模型输出里的 `closing` 字段就是这句话。流程是：

```
1) 发送 PDF「批改过程.pdf」
   （等 0.8~2 秒）
2) @提问者  批改报告发你了，主要错在最后那个加号上
```

要点：

- **`closing` 只在这次真的发了文件或图片时才有值**，纯文字聊天留空，不会出现多余的 @
- @ 由程序补（`onebot.send_group_at`），**模型只写要说的内容**，不自己写 `@某人`
- prompt 里明确禁止"希望这个回答对您有帮助""如有疑问请随时提问"这类客服话术
- 收尾话会**指出具体结论**（"主要错在最后那个加号上"），不是空泛的"做好了"

### 相关代码位置

| 干什么 | 在哪 |
|---|---|
| 起名规则、收尾话的写法要求 | `persona.py` 的 `OUTPUT_RULES` |
| 文件名清洗 | `brain.py` 的 `_safe_filename()` |
| 收尾话字段提取 | `brain.py` 的 `_normalize()` 返回值 `closing` |
| 用文件名发 PDF | `main.py` 的 `send_parts()` |
| 发完 @ 提问者 | `main.py` 的 `handle_message()` 末尾 + `onebot.send_group_at()` |

## 十四之二、批改类强制出 PDF（车主 2026-10-11 深夜定）

**背景**：群友发作业图说「@e阶导 批改一下」（**没提 PDF**）时，机器人只打字、不出报告。
统计 17 次批改类请求：**说了「要 PDF」的都出 PDF，没说的就纯打字**（还分了 4~5 条消息刷屏）。

**规矩**：**「被点名 + 带图 + 批改/订正/检查」→ 强制出 PDF 报告**，
不管群友有没有明说要 PDF。

```
被点名 + 带图 + 批改意图  →  强制 doc（PDF 批改报告）
其它情况                →  按体量自选（ZCode 那套规则不变）
```

**实现**（`main.py`，复用已验证有效的 `pdf_requested` 出口）：

```python
GRADE_HINTS = ["批改", "批阅", "订正", "改一下", "看看对不对", "检查一下",
               "检查下", "帮我看看", "对不对"]

def wants_grading_report(text, mentioned, has_image):
    if not (mentioned and has_image):
        return False
    return any(h in (text or "") for h in GRADE_HINTS)

# handle_message 里：
pdf_requested = (wants_pdf(text, mentioned)
                 or wants_grading_report(text, mentioned, bool(image_urls)))
```

### ⚠️ 这里有个重要教训：**行为习惯改不动，提示词不够**

我先**只在 `persona.py` 加提示词规则**（写了两条硬规则："批改类必须出 PDF"、
"纯文字上限 120 字"），**模型不照做** ——
规则确实部署并加载进 `PERSONA` 了（核对过），但实测还是 4 条文字 + 图，PDF=0。

**旧习惯「纯文字能说清就用纯文字」压过了新规则。**

**所以这种"行为偏好"级别的规则，必须用代码硬约束，不能只写提示词。**
（提示词保留作意图引导，但**兜底必须在代码里**。）

### 触发词偏宽的处理

`GRADE_HINTS` 里「对不对」可能误命中（"我说的对不对"），
但**要求同时满足「被点名 + 带图」**才生效，误伤概率低。
如果以后发现误伤，优先加前提条件而不是删词。

## 十四之四、报平安的两重校验（车主 2026-10-12 定）⭐ 保命功能

**为什么要改**：旧规则是「**任何私信消息 = 报平安**」。但**手机可能被人拿走**
（被胁迫、被抢）—— 那样发出来的"平安"是假的，**报警永远不会响**。
所以"能发消息"不再等于"人是安全的"。

### 新流程

```
【周五 20:00】
机器人 → 车主：「本周要开启周末平安值守吗？回复「是」我就开启（安全）」
车主 → 「是」
机器人 → 「✅ 已经成功开启…（安全）」

【周六 / 周日 · 当天第一次私信我时】
车主 → 任意一句话
机器人 → 「你真的平安吗？对一下我们的数字暗号（安全）」
    ├─ 回对暗号 ──────────────→ 「平安已记录 ✓（安全）」
    └─ 回错 / 不回
          ↓
       机器人 → 「数字不对。那对个只有我们知道的事：<秘密问题>（安全）」
          ├─ 答对 ───────────→ 「平安已记录 ✓（安全）」
          └─ 答错 / 15 分钟不回
                ↓
             🚨 私信紧急联系人，发车主约定的警报原文
```

### ⚠️ 三条绝对不能破的规矩

1. **暗号和秘密答案只能从 `.env` 读，绝不写进代码** ——
   一旦进公开仓库，**这套保护就形同虚设**。`.env` 已在 `.gitignore` 里。
2. **没配置暗号就不许开启**（`verify_configured()` 检查）——
   宁可明说"没保护"，也不能让车主**以为自己被保护着**。这是保命功能，不能有假的安心感。
3. **所有发给车主的安全类消息都带「（安全）」标记**（`_SAFE_MARK`）——
   车主靠它区分"必须回的安全消息"和"可以不急着回的闲聊"。

### 配置（都在 `.env`）

```bash
SAFETY_CODE=<SENSITIVE_C>                    # 数字暗号
SAFETY_SECRET_Q=你最喜欢的角色是谁？   # 秘密问题
SAFETY_SECRET_A=<SENSITIVE_B>                 # 秘密答案
SAFETY_VERIFY_TIMEOUT=900             # 问了暗号等多久没回就报警（秒，默认 15 分钟）
SAFETY_FRIDAY_ASK_HOUR=20             # 周五几点问"要不要开启"
SAFETY_ASK_WINDOW=86400               # 问了之后多久内回"是"还算数（秒）
```

### 改造时踩到/修掉的四个坑（都记下来）

| # | 坑 | 后果 | 修法 |
|---|---|---|---|
| 1 | `is_command()` 不认「是/否」 | 周五回「是」被当闲聊答掉，**开启指令丢失** | `is_command` 里加：有 `ask_ts` 时「是/否」也算命令（**pmchat 也必须避让**） |
| 2 | 校验进行中时 21:00 照常报警 | 车主 21:02 发消息 → **立刻误报**（人明明在） | 21:00 判定加 `not _ch_pending` —— 风险交给"15 分钟超时"那条兜 |
| 3 | 警报文案分散在两处 | 校验失败和到点未报要各写一遍 | 抽出 `_send_alert(day, why)`，每天最多一次 |
| 4 | `group_at()` 测试帮手匹配字面量 `"@20000"` | **永远匹配不到**（真实是 `{"type":"at","data":{"qq":"20000"}}`）| 按真实 at 消息段匹配。**这个帮手坏了很久没人发现，因为对应用例一直没被注册进运行清单（死代码）** |

> 💡 **教训**：定义在测试文件里 ≠ 会运行。**新增用例一定要记得加进运行清单**，
> 否则它会静默腐烂成一个"看着有覆盖、其实从没跑过"的假象。

### 测试

`tests/test_safety.py` 从 **35 项涨到 66 项断言**，新增覆盖：
当天第一条触发校验 / 暗号对 / 暗号错→秘密问答 / 两重都错→报警 /
15 分钟超时报警 / 每天不重复报 / **（安全）标记全覆盖** / 周五问+是 / 周五问+否 / 没配暗号拒绝开启。

## 十四之六、各线路速度实测（2026-10-12，判断"回复变慢"用）⭐

**为什么要记**：机器人的核心卖点是「**回复快**」。哪天群友说"变慢了"，
先看这张表判断是不是降级到了慢线路。

### 实测数据（同一提示词、`max_tokens=800`、各测 2~3 次取中位）

| 线路 | 模型 | 中位耗时 | 吞吐 | 识图 | 稳定性 |
|---|---|---|---|---|---|
| **主线路 / 备用1~3** | `deepseek-chat` | **0.89s** | 9.7 ms/tok | ✅ | 稳 |
| **备用7 方舟** | `deepseek-v4-1-flash-260910` | **1.39s** | 13.5 ms/tok | ✅ | 稳 |
| **备用4 千帆** | `deepseek-v4.1-flash` | **1.66s** | 12.2 ms/tok | ✅ | 稳 |
| 备用8 中转站 | `deepseek-4.1-flash` | 3.54s | 56.2 ms/tok | ? | 未知（中转）|
| 备用5 小米 Pro | `mimo-v2.6-pro` | 6.87s | 20.8 ms/tok | ✅ | 稳（**真思考 162 tok**）|
| 备用6 小米 Flash | `mimo-v2.6-flash` | **14.92s** | 105.0 ms/tok | ✅ | **极不稳**（26.3s / 3.6s）|

### ⚠️ 三个读表要点

1. **别只看秒数**：小米慢是因为**真思考了 162 个 token**（输出 331 tok），
   主线路只出 92 tok。**按 `ms/tok` 算差距会小一些** —— 但用户体感就是秒数。
2. **方舟比想象中快**（1.39s，比千帆还快）—— 因为它**关掉了思考**。
   这条线的速度优势以前被低估了。
3. **小米 Flash 极不稳定**（26.28s ↔ 3.55s）—— 不适合当主力，只适合垫底。

### 📊 降级实际发生频率（决定"排序值不值得优化"）

```
历史累计降级: 11 次
  全部是「主线路 → 备用1」   ← 同一个模型、同一速度（0.89s），用户无感
备用2 及以后: 0 次           ← 从来没被执行过

过去 24 小时: 353 次回复，降级 11 次（3%）
```

**结论：平时排序几乎不影响体验**（因为 99.7% 走主线路）。
**但官方 key 全部过期后**（预计 10-19 前后），降级链会真正走到第三方线路 ——
**那时候排序就决定了群友是 0.9s 还是 15s。**

### ✅ 排序原则是「到期优先」，**这是车主 2026-10-12 明确拍的板，不要"优化"成速度优先**

DSH 在 2026-10-12 提过一个建议：**把方舟（1.39s）提到小米（6.87s / 14.92s）前面**，
理由是"快是机器人的核心卖点"。**车主选择不改**，理由：

> **到期优先 = 不浪费额度。** 小米那条 11-10/40 天会过期，
> 排在前面能先把要过期的用掉；方舟的 50 万 token 不会过期，晚点用没关系。

**已经明确的代价（车主知情并接受）**：

```
10-19 前后（官方 key 全部烧完）之后，降级链会走到：
   备用5 小米 Pro（6.87s）→ 备用6 小米 Flash（14.92s）→ 备用7 方舟（1.39s）

→ 群友的回复速度可能从 0.9s 掉到 7~15 秒，而方舟（1.39s）排在它们后面。
```

**所以：哪天群友说"变慢了"，那是预期内的现象，不是故障。**
先按上面「排查变慢的步骤」确认走到了哪条线，再决定要不要重排。

> ⚠️ **改排序前先问车主。** 这是策略选择，不是技术问题。

## 十四之七、收尾话不许说假话（2026-10-12 事故，一天三次）⚠️

### 事故现象（车主原话）

> "有个人让你一次解决 10 道题，然后你就说解好了、已经发了，但 PDF 始终没有发。
> 我催你发 PDF，你再发群里了。"

### 日志铁证

```
11:26:26 [WARN] 所有片段都没发成功
11:26:29 收尾：发你了                                    ← 假话
11:27:13 群友：@<BOT_QQ> PDF发群里啊                    ← 群友只能再催
11:27:21 发送 PDF ✅（这次才真发出去）

11:42:23 渲染失败：正文过长（8060 字符，上限 8000）
11:42:26 收尾：PDF 发出来了，这题的关键是求导这一手         ← 假话
11:42:42 发送 PDF ✅（又是催了才发）
```

### 根因（**两个 bug 是连着的**）

**Bug 1 —— 收尾逻辑看的是「模型的计划」，不是「实际发没发」：**

```python
send_parts(group_id, result["parts"], style="")                # 返回值被丢掉了
sent_pdf = any(p["kind"] == "math" for p in result["parts"])   # ← 看「计划要发」
closing = ... if sent_pdf else ""
```

`send_parts()` 内部**明明有 `sent_any` 变量**，只是没返回、没人用。

**Bug 2 —— 正文上限 8000 太小，10 道题必撞墙：**

```
latex/render.py:  MAX_BODY = 8000
→ 渲染失败：正文过长（8060 字符，上限 8000）
→ 于是触发 Bug 1 说假话
```

### 修法

**① `send_parts()` 返回 `(sent_any, sent_doc)`：**

```python
def send_parts(group_id, parts, style="") -> tuple[bool, bool]:
    sent_any = False
    sent_doc = False          # 只有真的发出了 PDF 才为 True
    ...
    return sent_any, sent_doc
```

**② 两处调用方（主回复路径 + PDF 任务路径）都改成：**

```python
sent_any, sent_doc = send_parts(..., style=...)

if not sent_any:                      # 什么都没发出去
    if asker:
        onebot.send_group_at(group_id, asker, random.choice(FAIL_CLOSING))
    return                            # ← 绝不说"发了"

if sent_doc and not closing:
    closing = random.choice(CLOSING_FALLBACK)
```

**③ 新增诚实话术 `FAIL_CLOSING`：**

```
"不好意思，这份没排出来（我这边渲染失败了），你再说一声我重发一遍"
"刚才那份没生成成功，麻烦你再发我一次，我重做"
"这份我排版的时候挂了，没发出来。你再 @ 我一次我重试"
```

**④ 放开正文上限：**

```
latex/render.py  MAX_BODY:    8000 → 16000
brain.py         max_tokens:  8000 → 12000（PDF 模式）
main.py          max_tokens:  8000 → 12000（PDF 任务路径的另一处硬编码）
```

实测：**14108 字符（78 道题）的正文，xelatex 编译 1.5 秒** —— 离 60 秒超时很远。

### ⚠️ 部署时踩的坑（**改这里的人注意**）

`deploy.sh` 把**根目录的 `*.py` 装到机器人根目录**，只有 **`latex/*.py` 装到 `latex/`**。

我把 `latex/render.py` scp 到了部署目录根下 → **装错位置**（变成 `/home/qqbot/qq-bot/render.py`），
结果服务器上跑的还是旧的 8000 上限。

**正确做法**：

```bash
scp latex/render.py  root@服务器:/tmp/qqbot-deploy/latex/    # ← 必须进 latex/ 子目录
scp server/main.py   root@服务器:/tmp/qqbot-deploy/          # ← 服务端脚本放根目录
```

### 原则

> **宁可承认失败，也不说假话。** 群里的人可以接受"这次没成功"，
> 但接受不了"你说发了其实没发" —— **信任比功能缺失贵得多。**

回归测试：`tests/test_closing_honesty.py`（8 项断言：渲染失败 / 正常 / 只文字 / 卡片图 / 话术检查）。

## 十四之八、缺宏包导致整篇渲染失败（2026-10-12 第二次事故）⚠️

### 事故

群友引用图片说 `/pdf 充分性`，机器人回了「这道题我来答一下，发个 PDF」，
紧接着又说「批注看完了，充要两个方向都写了」—— **但 PDF 从头到尾没发出来。**

```
16:22:14  发送文字 15 字 ✅
16:22:17  渲染失败：l.121 证明：线性变换 $\mathscr{A}$ 可逆的充要条件...
                    ^^^^^^^^ Undefined control sequence
16:22:20  收尾：批注看完了，充要两个方向都写了    ← 假话
```

### 根因一：模板缺宏包

`\mathscr` 需要 `mathrsfs`，而三个模板都没加载。系统排查了 17 个常用命令，**缺 4 个**：

| 命令 | 缺的宏包 | 用途 |
|---|---|---|
| `\mathscr` | `mathrsfs` | 花体字母（**这次事故的元凶**）|
| `\bm` | `bm` | 粗体数学符号 |
| `\cancel` | `cancel` | 划掉 |
| `\coloneqq` | `mathtools` | 定义等号 |

**已给三个模板（card / doc / style2）都补上**，复测全部通过（各 1.4~1.8s）。

> 💡 **教训**：模型的 LaTeX 用词不可控，**模板要尽量全**。
> 缺一个宏包 = 整篇渲染失败 = 群友拿不到答案。
> 以后发现新的「Undefined control sequence」，第一反应是**补宏包**，不是让模型换写法。

### 根因二：**「部分成功」也会说假话**（上一版修复的漏洞）

`十四之七` 只堵住了「**啥都没发出去**」（`sent_any=False`）。
但这次是 **文字发成功、PDF 失败**：

```
sent_any = True    ← 有东西发出去了
sent_doc = False   ← 但 PDF 没发出去
```

于是**没走诚实分支**，而**模型自己给的收尾话照样发了出去** —— 又是假话。

**修法**：只要「**计划里有 PDF、但实际没发出 PDF**」，就用诚实话术**覆盖**收尾：

```python
planned_doc = any(p.get("kind") == "math" and p.get("mode") == "doc"
                  for p in result["parts"])
if planned_doc and not sent_doc:
    closing = random.choice(FAIL_CLOSING)     # 覆盖模型自己给的那句话
elif sent_doc and not closing:
    closing = random.choice(CLOSING_FALLBACK)
```

**两条路径（主回复 + PDF 任务）都改了。**

### ⚠️ 一条给我自己的教训

改代码时我在中文串里嵌了英文双引号，**同一个引号错误犯了三次**（
`log("...不说"发了"")`）。**以后写这类字符串一律用「」**。
另外：**扫描"可疑引号"没有意义，`py_compile` 全部文件才是真检查** ——
注释和文档字符串里的引号完全无害，编译不过才是真错。

回归测试：`tests/test_closing_honesty.py` 现在 10 项断言（新增「部分成功」用例）。

| 情况 | 接不接 |
|---|---|
| `/pdf` 开头 + 带图 | ✅ **接**（视同被点名 + 强制出 PDF）|
| `/PDF` / `／pdf` / 前导空白 / `/pdf详细`（没空格）| ✅ 都认 |
| 没图（只有 `/pdf`）| ❌ 不接（空喊，没题目可做）|
| `/pdf` 不在开头（正文里提了一句）| ❌ 不接 |
| `/pdfx`、`/pdfs` 这类近似词 | ❌ 不接 |
| **@ 了别的机器人** | ❌ 不接（不去抢别人的 @）|

### 实现（`server/main.py`）

```python
PDF_CMD_RE = re.compile(r"^[\s]*[/／]\s*pdf(?![a-zA-Z])", re.I)
# (?![a-zA-Z]) 必要：否则「/pdfx」也会被当成 /pdf

def is_pdf_command(text: str, has_image: bool) -> bool:
    if not has_image:
        return False
    return bool(PDF_CMD_RE.match(text or ""))


# handle_message 里：
pdf_shout = is_pdf_command(text, bool(image_urls))
if pdf_shout and not to_others:
    mentioned = True              # 视同被点名
    log("  ⭐ 「/pdf + 图」格式（群友在喊 PDF 机器人，没 @ 任何人）→ 接下")

pdf_requested = (wants_pdf(text, mentioned)
                 or wants_grading_report(text, mentioned, bool(image_urls))
                 or pdf_shout)     # /pdf 格式本身就明说要 PDF 交付
```

**`addressed_to_others` 那道门禁照旧** —— 别人明确 @ 了某个机器人，我们不去抢。

### 实测（端到端）

```
✅ /pdf + 图（不 @ 机器人）  →  📄PDF + ＠提问者 + 收尾话
✅ /pdf 没图                →  没动作
✅ 普通闲聊                  →  没动作
✅ @了凛凛音同学 + /pdf      →  没动作（不抢别人的 @）
```

边界用例 11 项全过。回归测试：`tests/test_pdf_shout.py`（19 项断言）。

> 💡 **这是"竞争"功能的第一个**：以前机器人是"被 @ 才动"，
> 现在多了一条**主动识别"群友在喊 PDF 机器人"**的路。
> 以后如果凛音同学还有别的固定格式，照这个思路加判定即可。

## 十四之十一、抄题复检（2026-10-12 定）⭐ 治「下标抄错 + 臆加条件」

### 为什么做

重要用户反馈：「出的解答有点简洁，**识别有的时候有点问题**」
车主补充：「**有一个题，那个二阶导它不是连续的，但你默认连续了**，后面让你改你才改对。」

### 触发条件（**只在两种情况**，不是所有图片请求）

| 触发 | 例子 |
|---|---|
| ① **要求详细/严谨** | 「详细解答下这个题」「严谨一点，一步步写」「写全」 |
| ② **二次追问**（说上次解错了/让重做）| 「你上次解错了，重新解」「这个不对，再算一遍」「刚才那题有问题」|

**为什么不全开**：复检 = **多一次视觉调用 + 慢约 1.5~2 秒**，
而「快」是机器人的核心卖点（见十四之六的速度实测）。只在这两种"值得多花时间"的场景开。

必须同时**被点名 + 带图**才成立 —— 没图的纯文字不存在"识别"问题。

### 怎么做

```
主调用之前，先单独跑一次视觉调用：**只抄题，不解题**

  brain.transcribe_problem(image_urls)
    ↓ 提示词只盯精度（下标/上标/条件/不许补条件/看不清就标[看不清]）
    ↓ 线路顺序 = config.PROVIDERS，**第一条就是 DeepSeek 主线路**（车主指定用 deepseek）
    ↓ 抄录结果并进主调用的上下文：
       「解题时拿它和原图互相核对；两处不一致就停下来确认，
         **绝对不许按「看起来应该是」去补题目没写的条件**」
```

**关键设计**：主调用要同时做「读题 + 解题 + 组织输出」，注意力被分散，下标容易抄错；
这一次**只干抄题一件事**，提示词也只盯精度。

**任何失败都返回空串**，调用方按「没复检」继续 —— **绝不让复检本身把回答搞挂**。

## 十四之十三、极致目标：群友永远不用重发（2026-10-12）⭐

### 事故

群友发手写图说 `/pdf 批改满分15` → **渲染失败** → 机器人回
「刚才那份没生成成功，**麻烦你再发我一次，我重做**」→ **群友就不太愿意再发了。**

**车主原话**：
> 「我们办事最好只办一次，**不要让群众跑几趟**。」
> 「实在不行还是要诚实说让他重发，**但要把这种情况的概率大幅下降，趋向于 0**。」

### 三层防御（从预防到兜底）

```
① 配平环境（渲染前预防）   render.balance_environments
       ↓ 救不了
② 自动修复（让模型修再重试） brain.fix_latex
       ↓ 还救不了
③ 诚实告知（最后手段，绝不说假话） main.FAIL_CLOSING
```

### 根因：模型写的 LaTeX 有两类"低级但要命"的问题

**系统测了 23 个常见写法**，找出原先会失败的：

| 情况 | 报错 | 现在 |
|---|---|---|
| `\begin{proof}` / `\begin{theorem}` / `\begin{lemma}` / `\begin{definition}` | `Environment ... undefined` | ✅ **补了 `amsthm` + 定理环境定义** |
| `\begin{itemize}` 忘写 `\end` | `\begin{itemize} ... ended by \end{document}` | ✅ **自动配平**（← **生产环境报的就是这个**）|
| 多余的 `\end{}` | 同上 | ✅ **自动删除** |
| 嵌套没闭合 | 同上 | ✅ **逆序补齐** |

**为什么补 `amsthm` 是大头**：模型写数学证明时**天天用** `\begin{proof}`，
而模板原先没加载 —— 等于每次写证明都在赌。

### ① 配平环境（`latex/render.py`）

```python
def balance_environments(body) -> tuple[str, list[str]]:
    """配平 \begin/\end。
      1. 没闭合的 \begin{X} → 末尾按**逆序**补 \end{X}
      2. 多余的 \end{X} → 删掉
    只在真的不平衡时才动，平衡的原样返回（绝不画蛇添足）。"""
```

接在 `sanitize()` 里（写 .tex 之前），修了什么会打日志（`[配平] ...`）。

### ② 自动修复（`brain.fix_latex`）

渲染失败后 → 把**出错的正文 + 报错信息**发回模型 → 要求**只修编译错误、不许改数学内容** →
拿到修好的正文**重试渲染**。走 `config.PROVIDERS`（第一条 DeepSeek）。

**任何失败都返回空串**，绝不让"修复"这一步把流程搞挂。

`send_parts` 里的逻辑：
```python
except Exception as exc:
    log(f"  渲染失败：{str(exc)[:600]}", "ERROR")   # 截断从 400 放宽到 600，方便诊断
    log("  🔧 尝试自动修复 LaTeX（不让群友重发）…")
    fixed = brain.fix_latex(part["latex"], str(exc))
    if fixed:
        path = latexrender.render(fixed, ...)     # 重试
```

### 实测

```
原先失败的环境：
  ✅ proof / theorem / lemma / definition
  ✅ itemize 忘闭合      → [配平] 补上没闭合的 \begin{itemize}
  ✅ 多余的一个 \end     → [配平] 删掉多余的 \end{itemize}
  ✅ 嵌套没闭合          → [配平] 补齐两层

自动修复：
  渲染失败 → 🔧 自动修复（45 字符）→ ✅ 重试成功，14977 字节 PDF 照常发出
```

回归测试：`tests/test_latex_robust.py`（19 项断言）。

> 💡 **原则**：**能自动救的绝不让群友做第二次。**
> 「让群友重发」是最后一道防线，不是第一反应。

## 十四之十四、对着 PDF 改 + 每题先抄题（2026-10-12）⭐

### 一、引用 PDF 让改 → **必须出新 PDF**

【⚠️ 这次是让**修改这份 PDF**，不是重新阅读】
必须输出一个 mode="doc" 的 math 片段（一份**修改后的新 PDF**），
把对方指出的问题改掉、其余内容保持完整。**不许只回文字说明。**

**注意**：只在**引用了 PDF** 的路径上生效（PDF 任务），

**实测**：

### ⚠️ 顺手抓到的自己的错（自检系统立功了）

问题位置：第 37 行 '\t'

**代价是服务进入崩溃循环**（自检失败 → 起不来），但这**远好过让模型收到被吃坏的 LaTeX**。

> 写完**本地先 `import persona` 跑一遍自检**再部署，别等服务崩了才发现。

## 十四之十五、用户纠错反馈自动收集（2026-10-12 定）⭐

### 定位：**核心是「纠错」**

车主原话：
> 「我的意思就类似于**纠错**吧，**别人指出你错误了**，这就属于我说的这种建议，
>  其他类似情况也算。」

采集重点：
| 类型 | 例子 |
|---|---|
| ① **解答/识别错了** | 「你第一题写错了」「下标抄错了」「**没说二阶导连续啊 你咋用了**」|
| ② **交付有毛病** | 「你这个PDF过程写的太简洁了」「下次记得批改时候要抄题」|
| ③ **行为该改** | 「下次记得批改要有得分」「以后能不能写详细点」|

**不收**：普通提问、客套、夸奖（宁缺毋滥，别让车主看噪音）。

### 两段式设计（判断要智能，但不能拖慢主流程）

```
① 即时抓取（廉价、无 LLM）
     handle_message 最前面：命中关键词预筛 → 立刻把**原始事实**落盘
     时间/谁说的/原话/引用了什么/最近几条上下文
     ⚠️ 放在最前面 —— 就算这条消息机器人不回复，纠错也不能丢

② 异步提炼（一次 LLM 调用，在主循环 tick 里做，一次一条）
     brain.judge_suggestion() 判断 + 分类 + 写清「错在哪·为什么错·怎么改」
     判完重写成可读版；判为「不是建议」的直接丢掉
```

**为什么分两段**：主流程一秒都不能拖。抓取零成本，提炼丢到后台慢慢做。

### 落盘

```
重要用户建议反馈/
  2026-10-12.md      ← 按天一个文件，人可读，追加式
  _待提炼.json        ← 还没过 LLM 的原始条目
```

**⚠️ 这个文件夹含真实群友消息，已加进 `.gitignore`，绝不公开。**
（`tests/test_feedback.py` 里有一项就专门检查这条规则；服务器上没有 git 仓库时会优雅跳过。）

### 实测（用日志里那个真实的"二阶导"案例）

自动生成的条目：

```markdown
## 18:34 · 你最近还好吗？ · 条件臆造 · 严重度 高

**他指的是**：对《批改过程.pdf》第2题（f二阶可导，证明存在ξ使f''(ξ)=2∫f）的批改

**原话**：> 没说二阶导连续啊 你咋用了 快重写
**他引用的内容**：> 【批改过程.pdf】第2题…
**机器人当时的回答**：> PDF《批改过程.pdf》1200字符；收尾「批改完了，12分」
**最近的上下文**：> - 123: /pdf 批改满分15（引用了一张手写图）

### 🔍 复盘
- **错在哪**：题目只给出 f 二阶可导，并未说明 f'' 连续，
             机器人却在证明中默认使用了 f'' 连续
- **为什么会错**：自行加强了题目条件，把「二阶可导」误当成「二阶连续可导」，
               属于条件臆造，导致证明逻辑不成立

### 💡 给开发 AI 的建议
重写该题解答：仅使用 f 二阶可导这一条件，改用不需 f'' 连续的论证方式
（如构造辅助函数用罗素定理两次，或对 f' 用拉格朗日中值定理），
并在输出前检查是否引入了题目未给的条件
```

**分类自动判成「条件臆造 · 严重度 高」** —— 正是最要命的那一类。

### 怎么用

车主随时可以说「把建议反馈调出来」，我读 `重要用户建议反馈/` 下的文件给汇总。

相关文件：`server/feedback.py`（采集+提炼）、`brain.judge_suggestion()`（LLM 判断）、
`tests/test_feedback.py`（24 项断言）。

## 十四之十六、数学分析陷阱库（2026-10-12 定）⭐ 提升能力的第一块

### 为什么是「陷阱库」而不是「题库」

车主的原始想法是搭一个数学分析题库（挑好题入库 + 提炼方法论）。
我把评估结论如实汇报后，改成**先搭陷阱库**（题库后做，定位改为"经典题快速索引"）。

**理由**：数学分析真正难的不是题型，是**条件的细微差别**：

```
二阶可导   ⇏ 二阶连续可导     ← 今天的真实事故
一致连续   ≠ 连续
逐点收敛   ⇏ 一致收敛
可积       ⇏ 有原函数
可导       ⇏ 导函数连续
```

| | 题库 | **陷阱库** |
|---|---|---|
| 一条的长度 | 几百~几千字 | **30~50 字** |
| 可验证性 | 难（要重算整题）| ✅ **好验**（摆个反例就清楚）|
| 直接治的病 | 泛泛 | ✅ **正好治「条件臆造」** |

### 数据文件

`docs/数学分析陷阱库.md`（**人可读、可直接手改、追加一节就生效**）

格式：
```markdown
## 二阶可导 ⇏ 二阶连续可导
- 标签: 导数 中值定理 泰勒 罗尔
- 陷阱: 题目只说「f 二阶可导」，**不能**默认 f'' 连续…
- 反例: f(x)=x⁴sin(1/x) (x≠0), f(0)=0。f'' 处处存在，但 f'' 在 x=0 不连续
- 正确做法: 用**两次罗尔定理**，或对 f' 用**拉格朗日中值定理**
- 来源: 群友指出（2026-10-12，《批改过程.pdf》第 2 题）★真实事故
```

**当前 23 条**，覆盖：导数/中值定理、一致收敛、级数、多元极限与偏导、
积分与原函数、含参积分、幂级数端点、傅里叶。

### 注入策略（**关键：只挑相关的**）

```python
trap_hint = traplib.hint(latest)     # 按题目关键词挑 3~6 条
```

**为什么不全量注入**：全量 3.7k 字符 ≈ 1.2k token，
而**现在整个 prompt 才 2.2k token** —— 每次都全塞会让成本和延迟涨 50%+。

实测注入量：

| 题目 | 注入 |
|---|---|
| 二阶可导那道（真实事故题） | 886 字符（≈295 token）**命中第 1 条就是它** |
| 证明 x^n 不一致收敛 | 748 字符（≈249 token）|
| 幂级数收敛域 | 671 字符（≈224 token）|
| **无关闲聊** | **0 字符** ✅ |

**没命中就注入 0 字符** —— 闲聊和小问题完全不受影响。

### ⚠️ 已知局限

**纯符号、没有中文关键词的题目可能不命中**（比如只写 `求 lim (tan x - sin x)/x^3`）。
现在的分词只看中文 n-gram 和英文单词，`lim`/`tan`/`sin` 这类不在标签里。
**缓解办法**：往对应条目的 `标签` 里补几个符号词（如「极限 洛必达 tan sin」）。
**真正常见的考研题都有中文描述，影响不大。**

### 怎么加条目

直接编辑 `docs/数学分析陷阱库.md`，追加一节（照上面的格式），**不用改代码**。
`traplib.py` 下次读文件就生效。

> 💡 **最值钱的种子已经有**：`重要用户建议反馈/`（十四之十五）收集的就是**群友指出机器人错在哪**
> —— 纠错点 = 模型真实的薄弱点，比"随机挑好题"精准得多。

相关文件：`docs/数学分析陷阱库.md`（数据）、`server/traplib.py`（解析+挑选）、
`tests/test_traplib.py`（断言）。

## 十四之十七、e阶导每日答疑讲义（2026-10-12 定）⭐

### 是什么

把当天所有答疑 PDF **合成一份长讲义**（带封面），凌晨固定时间发群里。
车主可以直接存到电脑；群友也有一份完整的当日合集。

**文件名**：`e阶导每日答疑讲义-YYYY-MM-DD.pdf`

### 三个设计决定（都是车主定的）

| # | 决定 | 理由 |
|---|---|---|
| **①** | **凌晨 00:10 汇总「前一天」**（不是 23:50）| 群里 **23:00 最活跃（实测 54 条/小时）**、00:00 还有 25 条。23:50 会切掉尾巴；00:10 完整覆盖，而且**不在「凌晨静默」（1:00–8:00）时段内** |
| **②** | **按 (提问者, 文件名) 去重取最后一版** | 修正时文件名通常不变（都叫「批改过程.pdf」），改对的版本**自动覆盖**旧的 |
| **③** | **空的日子不发** | 没题的日子发个空讲义没意义 |

### 实现

```

  build(day)                     合并：封面 + 当天所有 PDF → pdfunite
  maybe_run(group_id)            tick 到点触发（每天一次）
  _cleanup()                     留最近 DAILY_KEEP_DAYS 天，老的删掉
state/daily/YYYY-MM-DD/
  index.json                     当天清单（含 时间/提问者/文件名）
  01_xxx.pdf …                   另存副本（防 out/ 被清）
  e阶导每日答疑讲义-YYYY-MM-DD.pdf
```

**合并用 `pdfunite`（服务器自带）→ 零 API 成本、零依赖。**
**封面复用 doc 模板渲染**（不用新模板），内容：标题 + 日期 + 份数 + **本期目录**。

### 配置

```bash

DAILY_DIGEST_MINUTE=10        # 触发分钟

```

> 💡 **如果群友觉得每天一份太长，改成每周一期**：把触发改成周一、`build` 时汇总 7 天即可。
> 现在是**每天一期**，先跑着看反馈。

### 实测

## 十四之十八、每日讲义的两个坑（2026-10-12 当天踩的）⚠️

第一期讲义上线当天就连踩两个坑，**都记下来**。

### 坑一：**登记挂钩当天才上线，当天之前的 PDF 一条都没记上**

```
今天实际发送 PDF：54 次
state/daily/ 登记：0 条        ← 挂钩是当天晚上才加的
→ 今晚的讲义会是空的
```

**修法：加 `daily.backfill(day)` —— 从 `service.log` 回溯补录。**

解析依据：
```
决定回复（…）<名字>: …                          → 当时在跟谁说话
发送 PDF：ans_xxx.pdf → 群文件显示名「名字.pdf」   → 发了什么
收尾 @<qq>                                      → 收尾 @ 的是谁
```

**实测：一次补录 54 条，去重后 49 条，讲义 94 页 5.0 MB。**
补录是**幂等**的（按 `ans` 文件名判重），重复跑不会重复补。

> 💡 **教训**：**新功能的"登记"类挂钩，上线当天就要能回溯历史**，
> 否则第一天必然是空的。

### 坑二：**用户文本直接拼进 LaTeX → 封面整张渲不出来**

```
Missing character: There is no 👆 (U+1F446) in font   ← 群友昵称是纯 emoji
l.100 \item 08:20\quad 小意_OK\quad 批改过程
                            ^ Missing $ inserted       ← 昵称里的下划线
```

**两个错都让封面直接失败**（讲义还能出，但没封面）。

**修法：加 `_tex_escape()`，凡是要进 LaTeX 的用户文本一律先过它。**
```python
_TEX_SPECIAL = {"\\": ..., "&": r"\&", "%": r"\%", "$": r"\$", "#": r"\#",
                "_": r"\_", "{": r"\{", "}": r"\}", "~": ..., "^": ...}
# emoji / 非 BMP 字符 → 替换成「·」（LaTeX 默认字体没这些字形）
```

**顺带**：昵称**全是 emoji** 时，显示成孤零零一个「·」很难看 →
可打印字符为 0 时统一显示「**群友**」。

### 另外两处调整

| 项 | 改前 | 改后 | 原因 |
|---|---|---|---|
| `DAILY_DIGEST_MAX_PARTS` | 40 | **60** | 实测一天 49 条是常态，40 会**截掉当天一部分**（讲义不完整）|
| 去重窗口 | 无 | **30 分钟** | 否则同一个人间隔几小时发的两份「批改过程.pdf」**不同任务**会被错误合并 |

### 现在的结果

```
state/daily/2026-10-12/
  index.json                        49 条（含 时间/提问者/文件名/来源）
  01_xxx.pdf … 49_xxx.pdf           49 份副本
  e阶导每日答疑讲义-2026-10-12.pdf    94 页 / 5.0 MB
```

封面：`e阶导每日答疑讲义` + 日期 + 共 49 份解答 + 本期目录（时间/提问者/题名）。

## 十四之二十、讲义提前发进群了（2026-10-12 事故）🔴

### 现象

**晚上 20:03，群里收到了一份「e阶导每日答疑讲义」** —— 但触发时间设的是 00:10。
车主当场发现：「怎么直接把总讲义发群里了？还没到 12 点，现在才 8:03 呀。」

**日志确认发了**（而且因为我在反复重启调试，前后发了**两次**）：
```
19:04:18  已发群里：e阶导每日答疑讲义-2026-10-12.pdf
20:01:04  已发群里：e阶导每日答疑讲义-2026-10-12.pdf
20:03:03  已发群里：e阶导每日答疑讲义-2026-10-12.pdf
```

### 根因：**三个错叠在一起**

| # | 错 | 说明 |
|---|---|---|
| ① | **已发标记是内存变量** | `_last_run_day` 一重启就丢 → 以为「今天还没发过」|
| ② | **时间判断是「过了点就该发」** | `(20:03) >= (00:10)` 成立 → 认为到点该发了 |
| ③ | **`_target_day` 中午后返回「今天」** | 把**还没过完的当天**半截讲义发了 ❌ |

**核心错误是 ③** —— 讲义只能汇总**已经结束的完整自然日**，绝不能汇总「今天」。

### 修法

**① `_target_day` 永远返回昨天：**
```python
def _target_day(now: float) -> str:
    """最近一个**已经结束的完整自然日**（也就是昨天）。
    ⚠️ **永远不返回"今天"** —— 今天还没过完，出来的是残缺讲义。"""
    return time.strftime("%Y-%m-%d", time.localtime(now - 86400))
```

**② 已发标记持久化到 `.sent` 文件**（重启不丢）：
```python
def _sent_marker(day: str) -> Path:
    return _day_dir(day) / ".sent"
# maybe_run 里：
if _sent_marker(day).exists() or _last_run_day == day:
    return
```

**③ 「没内容」也落标记** —— 否则每个 tick 都重试一遍（每 2 秒一次）。

### 实测

```
各时刻会汇总哪一天（应该永远是昨天）：
  凌晨 00:10  → 2026-10-11
  早上 08:03  → 2026-10-11
  晚上 20:03  → 2026-10-11
  深夜 23:50  → 2026-10-11
  （今天 = 2026-10-12，始终没被汇总）✅

有 .sent 标记时（模拟重启后）调用 maybe_run → ✅ 没发
```

### 💡 教训

**「定时任务」必须满足两条，缺一不可：**

1. **只处理"已经完整结束"的周期** —— 别处理进行中的
2. **去重状态必须落盘** —— 内存变量在重启面前等于没有

> 我犯的正是「**用内存变量记"今天发过没有"**」这个经典错误。
> 而且是在**反复重启调试**的时候暴露的 —— 平时不重启还真看不出来。

## 十四之二十一、有精确解却给数值近似（2026-10-12 用户投诉）🔴🔴

### 用户原话

> 「这一点你做得非常不如英同学。用户表示了不满意，他说你这一题其实是有精确答案的，
>  那个英同学都算出来了，结果你用数值分析辛普森公式搞了个近似值就放上去了，
>  **考试他是不得分的**，因为考试能算出精确答案一定要算出精确答案。
>  就是考试是这样的，懂吧？不是做什么数值分析，它是**数学分析考试**呀。」

### 事故：一道定积分题，机器人错了**两次**

```
题目：I = ∫₋₁¹ eˣ·sin√(1−x²) dx

机器人的答案：
  ✅ 奇偶拆分做对了（eˣ 拆成 cosh 与 sinh，奇部积分为零）
  ❌ 然后说「没有初等原函数」→ 用 Simpson 给了 I ≈ 2.17808
  ❌ 结论写「积分的精确值没有初等表达式」
```

**错了两次：**

| # | 错 | 真相 |
|---|---|---|
| ① | **有精确解却给数值近似** | 精确值是 **π/2** —— 考试直接零分 |
| ② | **那个 2.17808 是编的** | 真值 1.5708，**差 0.607**。模型没有计算器，**数值结果是凭空虚构的** |

### 精确解 —— 关键一步是「认出单位圆」

我算了三种独立数值方法（直接 Simpson / 换元 / 奇偶拆分后），
**三者一致给出 1.570796326795 = π/2 精确到 12 位** ✅

解析证明（写进陷阱库了）：

```
I = Im ∫₋₁¹ e^{x+i√(1-x²)} dx
★ 认出 (x, √(1-x²)) 是**单位圆上的点**：
   令 x = cos φ  ⟹  x + i√(1-x²) = e^{iφ}
I = Im ∫₀^π e^{e^{iφ}} sin φ dφ
展开 e^{e^{iφ}} = Σ e^{inφ}/n!，逐项积分 ∫₀^π e^{inφ} sin φ dφ：
    n = 1    → iπ/2        （纯虚，贡献 π/2）
    n 偶     → 实数 2/(1−n²)（虚部为 0）
    n 奇(≥3) → 0
∴ I = π/2  ∎
```

### 修法：persona 加两条硬规则

```
⚠️⚠️ 考试类数学题（数学分析/考研）必须给精确解，绝不许用数值方法代替。
  ① 先假定有精确解，把该试的路走完再下结论：换元、对称性、奇偶拆分、凑微分、
     幂级数展开、交换求和与积分、参数求导、复化、认出「(x,√(1−x²)) 在单位圆上」…
  ② 「没有初等原函数」不是终点 —— 那只是「我没找到」，不是「不存在」。
  ③ 绝不用数值近似代替精确答案；真要给数值必须同时给精确形式并标注「这是近似值」。
  ④ 考试题能精确就必须精确 —— 近似值在考场上不得分。

⚠️ 你算不了数，绝不许编造数值结果。你没有计算器，
  任何「算得 ≈ 2.17808」这种具体数值都是编的。要么给精确表达式，
  要么老实说「具体数值需要实际计算」——不许编数字。
```

### 同时写进陷阱库（第 24 条）

`docs/数学分析陷阱库.md` 新增「★有精确解却去搞数值积分（考试直接零分）」，

### 实测：让机器人重做这道题

```

  ✅ 没用数值近似（不再出现 Simpson / 2.178）

  ✅ 奇偶拆分
  结论段：「作三角代换 x=cosφ，把根式化简，再用级数展开后逐项积分」← 正确路线

### ⚠️⚠️ 踩了一个很隐蔽的坑：**Ghostscript 压缩会把页眉丢掉**

一开始的实现是「**先盖章、再压缩**」，结果**页眉整段消失**，而且**不报错**。
逐步隔离才定位到：

```
盖章后的单文件        ✅ 有页眉
过一遍 pdfunite       ✅ 还在
过一遍 gs -dPDFSETTINGS=/ebook   🔴 丢了！   ← 元凶
```

**原因**：页眉用的是 PyMuPDF 内置 CJK 字体（`fontname="china-s"`），
Ghostscript 用 `PDFSETTINGS` 重写 PDF 时把它丢掉了。

**修法：调换顺序 —— 合并 → 压缩 → 再盖章。**
配套改动：盖章从「按分册盖」改成「**按页码区间盖合并后的成品**」
（要先算出封面页数和每份分册的页数）。

**另外还踩了一个**：盖章是在 `build()` 清理完 `_build/` 之后才调的，
`doc.save()` 直接报 `No such file or directory`。
修法：盖章函数自己 `mkdir(parents=True, exist_ok=True)`。

> 💡 **教训**：**"不报错"不等于"做成了"。**
> 盖章这一步从头到尾没抛异常，日志也写着"已给 60 份盖上题号页眉"，
> 但成品里一个字都没有 —— 是**最后逐页检查文本才发现的**。
> 涉及"改内容"的步骤，**必须验证产物本身**，不能只看返回值。

## 十四之二十九、识图 API（Gemini 认手写）—— **和答疑 API 分开**（2026-10-13 定）

### 车主的需求

> 「接我们叫**识图 API**，跟**答疑 API 不一样**，懂吧？
>  正常的图片或者 PDF 让你答疑，你就正常 DeepSeek v4.1 识别就行了。
>  然后如果是**手稿**，就是纸上手稿写的题目，那识别就有难度了，
>  所以你就用 **Gemini 3.8 Flash** 这个 API 识别，这个会比较慢，
>  然后识别好了，你再交给 **DeepSeek 去解答**就可以了。
>  因为群友反映 Gemini 在**草稿的识图上**比较好，导致大家都去用那个凛音同学了，
>  **草稿批改，就手写的草稿纸，所以你这必须要做到。**」

### 分工

```
手写草稿/拍照纸面 ──→ 识图 API（Gemini 3.8 Flash High）抄题 ──→ DeepSeek 解答
干净图片/PDF      ──→ 直接 DeepSeek（快得多：0.8s vs 8.9s）
```

**关键：识图 API 只负责"抄题"，解答仍然是 DeepSeek** —— 识图归识图，答疑归答疑。

### 三块实现

**① 手写判定（本地算，不花钱）** —— `vision.looks_handwritten()`

⚠️ **阈值是实测校准的**，不是拍脑袋：

| 样张 | 纸面亮度 | 对比 | 格式 |
|---|---|---|---|
| 干净渲染图（截图）| **255.0** | **0.0** | PNG |
| 白底 PNG | **255.0** | **0.0** | PNG |
| 拍照模拟·中退化 | 243.6 | 20.3 | JPEG |
| 拍照模拟·强退化 | 233.5 | 25.3 | JPEG |

**两组分得很开** —— 纯白截图的纸面恒为 255、对比恒为 0。
判据：`纸面 < 250 或 对比 > 8`（外加 JPEG 且纸面 < 253）。

⚠️ **判错的代价不对称**：
- 误判成手写 → 只是多花几秒
- 误判成截图 → **手写题可能被读错，答案就错了**

**所以宁可宽松**，判不出来时**按手写处理**。校准结果 4/4 正确（含"干净图存成高质量 JPEG"的
反例 —— 不能被误判）。

**② 识图路由** —— `brain.transcribe_problem(images, prefer_vision_api=True)`
先走 Gemini，失败自动回退到普通线路；**任何失败都返回空串**，绝不影响回答。

**③ 主流程** —— `main.py` 检测到手写就**强制复检**（`recheck=True`）：
手写稿必须先抄准，读错了后面全错。

### 实测

```
【手写草稿】37.1s
  ✍️ 判定为手写草稿 → 用识图 API（Gemini）抄题，解答仍交给 DeepSeek
  🔍 识图 API（gemini-3.8-flash-high）抄题成功：130 字符，10.0s
  → 发 PDF「积分型中值定理解答.pdf」

【干净印刷图】5.7s
  （没有手写判定，直接 DeepSeek）→ 发 PDF「定积分解答.pdf」
```

### ⚠️ 两个坑

**坑① 模型 id 是 `gemini-3.8-flash-high`，不是 `gemini-3.8-flash`**
```
gemini-3.8-flash       → HTTP 503 No available channel for model ...
gemini-3.8-flash-high  → ✅ 可用
```

**坑② 车主给的那把新 key 是无效的（HTTP 401 Invalid token）**
**决定性对照**（同一端点、同一模型）：
```
现有 key（备用9）→ HTTP 200  ✅
新 key          → HTTP 401  {"message":"Invalid token"}  ❌
```
所以**默认借用中转站那把 key**（实测能调 gemini）。
新 key 生效后，在 `.env` 里填 `VISION_API_KEY` 覆盖即可。

**另外**：relay 的 `/models` 返回的是**网站 HTML**（不是 JSON），
所以"列模型"这条路走不通 —— 只能直接试模型 id。

### 配置

```bash
VISION_API_BASE=https://api.bingheai.org/v1
VISION_API_MODEL=gemini-3.8-flash-high
VISION_API_KEY=            # 留空则自动借用中转站的 key
VISION_HANDWRITING=1       # 手写识别总开关；关掉则所有图都走 DeepSeek
```

## 十四之三十、`/pdf` 不带图也要接（2026-10-13 车主纠正）🔴

### 事故

群友在群里打了：

```
/pdf 中国近代史到新中国成立前马克思主义中国化的进程      ← 纯文字，没有图
```

**凛音同学答了**（群里截图可见它发了「正在生成中…」），**我们没答** ❌ —— 白送用户。

### 根因

我一开始的 `is_pdf_command()` **要求必须带图**：

```python
def is_pdf_command(text, has_image):
    if not has_image:
        return False          # ← 就是这里挡掉了纯文字请求
    return bool(PDF_CMD_RE.match(text or ""))
```

当时的想法是"没图就是空喊，不接"。**但车主纠正得对**：

> 「**只要出现了 /pdf 开头的问题，你都要回答**，那个凛音同学都会自动回答。」

`/pdf` 本来就是群里的**约定暗号** —— 开头写了 `/pdf` 就是明确在喊，
**纯文字（比如让总结知识点）也一样要接**。

### 修法

```python
def is_pdf_command(text: str, has_image: bool = False) -> bool:
    """以 /pdf 开头就接，**不看有没有图**。
    `has_image` 参数保留只为兼容调用方，不再参与判断。"""
    return bool(PDF_CMD_RE.match(text or ""))
```

**仍然守住的边界**：
- `/pdfx`、`/pdf2` → 不接（正则 `(?![a-zA-Z0-9])`）
- 不是开头的「我想看 pdf」→ 不接
- **别人 @ 了别的机器人 → 不抢**（`addressed_to_others` 门禁照旧）

### 实测

```
【纯文字 /pdf】8.7s
  ⭐ 「/pdf …」喊话格式（群友在喊 PDF 机器人，没 @ 任何人）→ 接下
  发送 PDF →「马克思主义中国化进程.pdf」
  收尾 @3132885821：整理好了，按四个阶段理的，你看看对不对
```

**边界用例 10/10 通过**（含大写 `/PDF`、全角 `／pdf`、前导空格、`/pdf详细说明`）。

> 💡 **教训**：**"宁可漏不可误伤"这条原则，在"暗号"场景下是错的。**
> 暗号（`/pdf`）本身就是为了**明确表达意图**而存在的 —— 用户特意打了这个前缀，
> 就是在说"我要这个"。这时候还去猜"他是不是随口提一句"，等于把用户推走。

## 十四之三十四、「留给你自己验算」= 敷衍（2026-10-13 事故）🔴

### 事故

群友 y 发了道题：`/pdf 三种方法解决，我是小学生`（2019A02 范德蒙行列式 + 代数余子式求和）。

```
[5] y:      你写错了 @e阶导
[6-7] 凛音:  @y + [文件]（正确答案）
[8] y:       @凛音同学 你写对了
```

**我写了个 0** —— **错的。**

### 我的错在哪（两层）

**第一层：我给了一个没算过的结论。** 而且 0 这个数**看起来很干净** —— 恰恰最可疑。

**第二层（更根本）：我跳过了关键计算，还写「留给你自己验算」。**

原话：
> 「直接代进去化简（**这一步是纯代数，留给你自己验算**）依然得到 tr(A⁻¹F) = 0」

**这是推卸责任。** 读者拿到的是**半份解答** —— 就算他真去验算，
也是在一个错结论的引导下去算；而绝大多数人不会验算，只会记住那个 0。

### 正确答案

$$\sum_{i,j=1}^{2019}(x_i^{2019}+j^{70})A_{ij}=|A|\cdot\Bigl(2-\prod_{k=1}^{2019}(1-x_k)\Bigr)$$

**两步推导**：
1. **A 的第一列全是 1** → 把第 j 列换成全 1 列，j≠1 时与第 1 列相同 → 行列式为 0；
   j=1 时就是 |A| 本身。故 `∑_i A_ij = δ_j1·|A|`，于是 **`∑ j^70·A_ij = 1^70·|A| = |A|`**。
2. **拉格朗日插值在 t=1**：`1 = ∑_i x_i^n·L_i(1) + ∏_k(1−x_k)`，
   而 `∑_j A_ij = |A|·L_i(1)` → **`∑ x_i^n·A_ij = |A|·(1−∏(1−x_k))`**。
3. 合计 = `|A|·(2−∏(1−x_k))`。

### ⚠️ 验证时又踩了一个坑：**浮点相消**

我写完推导后想数值验证，用浮点算 `∑ j^70·A_ij`，得到 **−9.28e26** ❌ ——
差点让我以为公式错了。**其实是灾难性相消**：
`2^70 ≈ 1.18e21`，乘上"理论上为 0 但浮点不为 0"的余子式和，
**把其他项的有效数字全冲光了**。

**改用精确分数（`fractions.Fraction`）后，三个 n 全部精确吻合** ✅

> 💡 **教训**：**验证要选对数值方法。** 大数和小量混在一起时，浮点会给出假象 ——
> 用精确分数或符号推导，别急着下结论。

### 修法

**persona 加硬规则**：
```
⚠️⚠️ 绝不许跳过关键计算，更不许写「这一步留给你自己验算」。
  ① 关键步骤必须自己算完 —— 用「留给你自己验算」「不难验证」「显然」「同理可得」
     跳过，是推卸责任，读者拿到的是半份解答，错了他也不知道。
  ② 没有真正算出来，就不要写结论。尤其别写「=0」「=1」这种看起来很干净、
     但你根本没验证过的数。**干净的结果最容易是编的。**
  ③ 想确认就真去确认：符号推导 / 精确分数 / 小规模数值代入
     （⚠️ 注意浮点相消，得用精确分数算）
```

**陷阱库加了第 25 条**（含完整正确解法），检索关键词覆盖
代数余子式 / 范德蒙 / 拉格朗日插值 / 行列式。

> 「这条我没法直接对上原图的具体式子……**为了不给你一份瞎编的答案**，
>  这里把补全 P⁻¹ 这一步的**通用套路**写清楚……」
>
> 「一、P⁻¹ 通常怎么来的：一般 P⁻¹ 出现在**递推型**计算里……
>  情形 A：由递推式外推 P_{n+1} = a·P_n + b……情形 B：由通项公式代入 n = −1……」

**群友要的是矩阵 P 的逆，机器人讲的是数列的 P₋₁。** 完全答非所问。

**根因**：`P⁻¹` 符号有歧义，机器人**挑了最省事的那个解释**，
而且**没有回看自己之前那条回答**（上下文里全是特征值/特征向量/`PΛP⁻¹`，
显然就是矩阵的逆）。

### 错误二：P⁻¹ 第一行第二列写成 −3/2（应为 −5/2）

```
机器人写的：  ⎡  3   −3/2   1/2 ⎤     ← 整份文档里**根本没出现过数字 5**
             ⎢ −3     4    −1  ⎥
             ⎣  1   −3/2   1/2 ⎦

正确的：      ⎡  3   −5/2   1/2 ⎤
             ⎢ −3     4    −1  ⎥
             ⎣  1   −3/2   1/2 ⎦
```

**但真正的病灶不是算错，是"没被用上"**：

> 「这里因为 2, −2, 1 就是 β 在这组基下的坐标，**故直接读出即可**。
>  （若需要显式写出 P⁻¹，则 P⁻¹ = [...]）」← 括号里这个**从没验算过**

最终 Aⁿβ 是用**从第(1)问读出的坐标 (2,−2,1)** 算的，**没乘这个 P⁻¹** ——
所以**最终答案是对的，错的矩阵就混在答案里没人发现**。

如果当时花 10 秒验一下 `P·P⁻¹ = I`：
```
P 第1行 · 错P⁻¹ 第2列 = [1,1,1]·[−3/2, 4, −3/2] = 1 ≠ 0   ← 一眼露馅
```

### 修法：persona 加两条硬规则

```
⚠️⚠️ 凡是写进答案的数字和矩阵，都必须被用到、或被验算过。
  ① 逆矩阵算完必须验算 P·P⁻¹ = I（10 秒的事）。
     行列式用展开式或代特殊值复核；矩阵乘法代具体数字复核。
  ② 凡写进答案的数，都要么被后续步骤真正用到，要么被独立验算过。
     「没用上也没验过」的数是最危险的 —— 错了也没人知道。
  ③ 别为了凑一个"完整"的答案，把没算过的东西塞进去。

⚠️ 收到「补全 / 续写 / 接着上面」这类要求，先回看自己之前那条回答。
  ① 「补全 X」= 对方在指某份已有内容，先搞清楚是哪份、指哪个对象。
  ② 符号有歧义时按上下文判断，别挑最省事的那个解释。
  ③ 真拿不准就先问一句，比写一大篇错的好得多。
```

**陷阱库加了 2 条**（第 26、27 条），含完整正确解：

```
P = [[1,1,1],[1,2,3],[1,4,9]]（范德蒙德矩阵的**转置**），det P = 2
P⁻¹ = [[3, −5/2, 1/2], [−3, 4, −1], [1, −3/2, 1/2]]
P⁻¹β = (2, −2, 1)ᵀ
Aⁿβ = (2 − 2^(n+1) + 3ⁿ, 2 − 2^(n+2) + 3^(n+1), 2 − 2^(n+3) + 3^(n+2))ᵀ
数值验算：n=1 → (1,3,13)；n=2 → (3,13,51) ✅
```

**检索实测**（三条查询都精确命中）：
```
「求矩阵P的逆，特征值特征向量那题」→ ★逆矩阵算完必须验算
「补全方法2 P-1计算结果」        → ★「补全 X」要先回看自己之前说过什么
「怎么验算逆矩阵」              → ★逆矩阵必须验算 + ★不许「留给你自己验算」
```

> 💡 **教训**：**最危险的不是算错，是"错了也没人知道"。**
> 算错至少还有验算能拦；**而一个既不参与后续推导、又不被验算的中间结果，
> 完全处在所有检查之外** —— 它是答案的一部分，却没有任何环节为它负责。

## 十四之四十一、播报必须「**调用成功了才说**」（2026-10-14）🔴

>  **你确保这次能请求成功以后，你再回复那句话**……
>  **不要骗人**。」

### 我原来的实现：**调用前就播报** ❌

```python
_provs, _hard = providers_for(text)
if _hard:
    announce_named_line(group_id, _provs[0])     # ← 调用之前就把话说出去了
result = brain.decide(...)
```

**后果**：那条中转站 429/404 挂了 → 自动降级到 DeepSeek 答 →
**群里看到「这题请 Opus 5.5 出手」，答案其实是 DeepSeek 给的** ❌

**这跟之前"说假话：文件发了"是同一类错误** —— 都是"先宣称、后兑现"。

### 修法：三处一起改

**① 播报挪到所有 `decide` 跑完之后**（`result` 定稿才说）
```python
result = brain.decide(...)
_model_note = announce_named_line(group_id, _provs[0], result.get("provider") or "") if _hard else ""
```
⚠️ **不能只挪到第一次 decide 之后** —— `handle_message` 里还有个
**强制 mode 的重试 decide**，重试成功会替换 `result`。
必须放在**所有** decide 之后（用 AST 检查确认：`min(announce) > max(decide)`）。

**② 重试也要带同一条线路**
```python
_retry = brain.decide(..., force_mode=_force_mode, providers=_provs)   # ← 原来漏了
```
漏了的话重试会走默认线路（DeepSeek），而播报已经说了"Opus 算的" —— **还是骗人**。

**③ 播报分三种情况说人话**
```python
if answered_by != name:          # 点名线没答成
    → 「Opus 5.5 那边这会儿连不上，我先用常规线路给你答了」（说实话）
    → PDF **不印**小字
else:                            # 点名线真的答成了
    → 「用 Opus 5.5 给你算的，你看看」
    → PDF 印「本题由 Opus 5.5 协助作答」
# 没点名 → 不播报
```

**文案也跟着改成事后口径**（「用 XX 算的」而不是「请 XX 出手，稍等」）——
因为话是说在**算完之后**的，用"稍等"会跟事实不符。

### 实测三种情况

```
① 点名 opus，线路正常
   📣 已播报（确认由「Opus5.5」作答）：用 Opus 5.5 给你算的，你看看
   1. 用 Opus 5.5 给你算的，你看看
   2. 1+1=2 😅

② 点名 opus，那条线挂了（把 base_url 指向不存在的地址模拟）
   📣 点名线未答成，已如实播报：Opus 5.5 那边这会儿连不上，我先用常规线路给你答了
   ⚠ 「Opus5.5」不可用，本次由「备用1」作答
   1. Opus 5.5 那边这会儿连不上，我先用常规线路给你答了
   2. 2。这题用不着 Opus，用草稿纸就够了 😅

③ 没点名 → 不播报
```

### ⚠️ 顺手识破一个**AST 误报掩盖的真 bug**

我先用 AST 检查「announce 是否在 decide 之后」，`handle_message` 报 🔴，
我以为是误报（因为里面有两个 decide）。**结果顺着查下去发现是真的** ——
第二个 decide（重试用）确实在 announce 之后，而它会替换 `result`。
**差点把真 bug 当成工具误报放过。**

> 💡 **教训**：**工具报红时，先假设它是对的，去查清楚再说"误报"。**
> 我这次是先怀疑工具、后证实工具 —— 顺序反了会很危险。

### 💡 核心原则（值得记牢）

**宣称必须由结果驱动，不能由意图驱动。**
- ❌ 「我请了 Opus」→ 然后调用
- ✅ 调用了 → 看返回 → 「这条是 Opus 算的」

同一原则已经用过三次：
1. 说"文件发你了" → 改成看 `send_parts` 的返回
2. 说"页眉盖好了" → 改成**打开成品逐页检查**
3. 说"路由给 Opus 了" → 改成**等 API 真的返回 200**

### 坑 5：模型写的**字面 `\n`** 把 LaTeX 编译搞炸（2026-10-11，一天内两次）

**症状**：PDF 渲染失败，日志里是

```
渲染失败：/home/qqbot/qq-bot/out/render-xxx/ans_xxx.tex:64:
Undefined control sequence.
l.64 \section*{题目}\n设 $0<a_n<1$...
```

**根因**：模型在 JSON 里写 `\\n`（本想表示换行），JSON 解析后变成
**字面的两个字符「反斜杠 + n」**，直接进了 `.tex` —— LaTeX 把 `\n设` 当成一个命令。

**后果比"渲染失败"更糟**：所有片段都没发成功，但收尾话还说「订正版附上了」，
群友追问「批改完了 PDF 咋不发」。**等于对群友说了假话。**

**修法**（在 `server/latexrender.py`，一行）：

```python
_LITERAL_NEWLINE = re.compile(r"(?<!\\)\\n(?![A-Za-z])")
body = _LITERAL_NEWLINE.sub("\n", body)
```

⚠️ **`(?![A-Za-z])` 这个条件绝对不能省！**
`\n` 是 `\neq` / `\nabla` / `\newline` / `\node` / `\noindent` 这些命令的开头，
无脑替换会把 `\neq` 变成 `eq`（数学公式静默出错，比编译失败更难发现）。
加了"后面不跟字母"之后，只有"后面是中文/标点/行尾"才算误写的换行。

**回归测试**：`tests/test_latex_newline.py`（18 项断言，纯函数不依赖 LaTeX，
本地和服务器都能跑）。里面专门列了 10 个以 `\n` 开头的命令做"不能动"的检查。

**还没修的相关问题**：`main.py` 里"所有片段都没发成功"时仍会发收尾话
（`send_parts` 失败没有回传结果给收尾逻辑）。所以渲染修好之后，
**万一还有别的渲染失败，机器人仍可能说"附上了"而实际没发**——见下方待办。



### 坑 1：把「聊天里提到 PDF」当成「要 PDF」（2026-10-10 事故）

**现场**：群里有人 @ 了另一个机器人（凛音同学）让它解题，muse 在旁边聊天说
「凛音别上来就甩PDF啊，我蹲一个解题过程看你说人话不」。
结果我们的机器人**冒出来发了一份「解题过程.pdf」，内容跟任何题目都对不上**。

**原因**：`wants_pdf()` 当时只做了一件事——

```python
return any(h in text.lower() for h in PDF_HINTS)   # 只要消息里出现 "pdf"
```

**任何人只要在聊天里打出 "PDF" 三个字，就会被判定成"要一份 PDF"**，
然后 `pdf_requested=True` 会强制模型输出 `mode: doc`。
可那条消息根本没有题目，模型被逼着出文档，只能瞎写。

**修法**（两层）：

1. `wants_pdf(text, mentioned)` 现在**必须同时满足**：① 点名了机器人 ② 提到 pdf。
   没被点名时，说到 PDF 顶多是在讨论这个格式
2. prompt 里给它**逃生口**：如果判断对方其实不是在要 PDF（只是在聊格式、评价别人的 PDF），
   就正常回复或直接 ignore，别硬造文档

**回归测试**（写在改动里，改这块时一定要重跑）：

| 消息 | @bot | 会不会强制 PDF |
|---|---|---|
| `凛音别上来就甩PDF啊…` | ❌ | **不会** ✅ |
| `这个 PDF 阅读器挺好用的` | ❌ | **不会** ✅ |
| `@机器人 帮我出个 PDF` | ✅ | 会 |
| `@机器人 解决此题` | ✅ | 不会（但照常解答） |

**教训**：**「交付形式」和「用户意图」是两回事。** 关键词匹配只能当辅助信号，
决定要不要走重流程（生成文件）时，必须加上"这是不是在对我说话"这个前提。

### 坑 2：在别人说话时插嘴（同一天）

**现场**：群里 @ 的是**另一个**机器人（凛音同学）、或者有人在跟别人说话，
我们这台也跟着冒出来。最典型的就是上面 muse 那句 —— 里面「凛音」是**纯文本、
不是 @ 段**，所以 `mentioned=False`，可它仍然被「问句/数学词/闲聊」规则捞起来回了。

**根因**：触发逻辑里有**太多"没被点名也能回"的路径**：

```python
if is_question(text) and ...prob:      # 问句就回
if any(w in text for w in MATH_WORDS): # 有数学词就回
if ... < params["idle"]:               # 闲聊插嘴
```

这些路径在"有人跟别人说话"时会疯狂误伤。

**修法**（三道闸，全在 `main.py`）：

1. `addressed_to_others()` —— 消息 @ 了别人，**或者文字里出现 `IGNORE_NAMES` 里的名字**
   （凛音、凛音同学、muse…），一律直接不接
2. `MENTION_ONLY`（默认开）—— 没被点名的消息**一律不接**，
   问句/数学词/闲聊规则全部不生效
3. `IDLE_CHAT_ENABLED`（默认关）—— 把「闲聊插嘴」概率归零

**教训**：**"能不能回"和"该不该回"要分开管。**
触发条件越宽松，误伤越多。默认应该是最严格的（只认点名），
额外的活跃度当成显式开关，由人来决定开不开 —— 而不是默认开着一堆概率规则。

### 坑 3：静默吞异常，制造"看起来正常"的假象

**现场**：给机器人加了「自动识别自己当前名字」的功能（因为车主改过好几次名）。
部署后日志正常、测试也通过，**但识别集里只有兜底那一个 `阶导`**——
昵称和群名片一个都没抓进来。

**根因**：漏了 `import re`，`re.sub` 抛 `NameError`，而代码写的是：

```python
try:
    names |= _name_variants(...)
except Exception:
    pass          # ← NameError 被这里吃掉了
```

于是它**退化成"只靠兜底字符串工作"**。因为兜底的 `阶导`
恰好是新名字 `e阶导` 的子串，所以一切看起来都正常 —— 最难发现的那种 bug。

**修法**：

1. 补上 `import re`
2. **把 `except Exception: pass` 改成记日志**（`log(..., "WARN")`），
   失败必须留痕，不能再静默

**教训**：**`except: pass` 是给自己埋雷。** 尤其是在"失败了也能跑、
只是退化"的场景里 —— 它会把"功能没生效"伪装成"功能正常"。
要么让异常冒出来，要么至少记一条日志。另外，**兜底值太巧（正好是子串）
会掩盖真实故障**，写测试时要断言"抓到了完整集合"，不能只看"能用"。

### 坑 4：提示词里的单反斜杠被 Python 吃掉（2026-10-10）

**现场**：给提示词加表格说明时写了：

```python
【表格】用 booktabs 出三线表：`\toprule` / `\midrule` / `\bottomrule`
```

Python 把 `\t` 当**制表符**、`\b` 当**退格符**，于是模型实际收到的是：

```
「⇥oprule」和「⌫ottomrule」   ← 前面是控制字符，不是反斜杠
```

**模型一直在读损坏的表格语法**，还能画对三线表纯粹是靠训练常识兜着。

**为什么难发现**：这类损坏**不报错、不崩溃**。`\m`（`\midrule`）会发一条
`SyntaxWarning`，但 `\t` / `\b` / `\n` 是**合法转义**，静默变形，
只能靠比对运行时字符串才能发现。

**哪些会坏、哪些不会**（重要，省得白排查）：

| 源码里写 | Python 解析成 | 后果 |
|---|---|---|
| `\toprule` | 制表符 + oprule | 🔴 静默损坏 |
| `\bottomrule` | 退格符 + ottomrule | 🔴 静默损坏 |
| `\node` | 换行 + ode | 🔴 静默损坏 |
| `\theta` | 制表符 + heta | 🔴 静默损坏 |
| `\documentclass` | 原样保留（`\d` 非法转义） | 🟡 只报警告，**不损坏** |
| `\usepackage` | 原样保留 | 🟡 只报警告，**不损坏** |
| `\[` / `\]` | 原样保留 | 🟡 只报警告，**不损坏** |

所以**别拿 `\documentclass` 去测这个自检**，它测不出来 —— 要用 `\toprule`。

**修法 + 防复发**（两个文件各一套，因为情况不同）：

| 文件 | 做法 | 为什么不同 |
|---|---|---|
| `persona.py` | 扫**源文件**里 `PERSONA`~`OUTPUT_RULES` 区间内的「单反斜杠+字母」 | 这份文件里所有反斜杠都该是双的 |
| `brain.py` | 扫**运行时字符串** `PDF_HINT` / `IMAGE_HINT_TEMPLATE` 里的控制字符 | 这份文件里有正当的单反斜杠（正则、`r"\textbackslash{}"`），不能扫源码 |

两个自检都在**模块导入时执行，发现就抛异常** —— 宁可启动就炸，
也不要带着坏提示词悄悄跑。

⚠️ 自检**不要扫拼接后的完整提示词**：群聊上下文和用户消息是拼进去的，
里面出现制表符是正常的，会误报。只查静态文案（静态文案一律用空格缩进）。

**写这个自检本身也踩了三个坑**（留个记录，别再犯）：

1. 第一版扫运行时字符串找控制字符，但**排除了制表符**（多行文案里它合法）
   → 恰好漏掉 `\toprule` 变制表符这种情况
2. 第二版改成扫**整个源文件** → 太激进，**把自检函数自己的注释和代码抓了**
   （注释里举反例也要写单反斜杠、代码里 `count("\n")` 是语法），服务直接崩溃重启
3. 第三版：限定区间扫描，才正确

**教训**：**在满是中文和 LaTeX 的提示词文件里，反斜杠是雷区。**
这类问题应该在**部署时**就拦住，而不是等模型输出变奇怪了再回头查 ——
因为它的症状（"表格画得时好时坏"）离病因（"提示词里少了几个反斜杠"）太远了。
