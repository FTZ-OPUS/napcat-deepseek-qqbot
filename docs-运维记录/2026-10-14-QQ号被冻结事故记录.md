## 二、根因分析

### 直接原因：腾讯风控判定为异常账号 → 冻结

### 行为特征（我的分析）

| 行为 | 数据 | 风控敏感度 |
|---|---|---|
| **大量文件传输** | 10-13 一天 **104 份 PDF** | 🔴 **极高** —— 正常用户一天发几份顶天了 |
| **高频自动回复** | 一天 **211 次**，几乎秒回 | 🔴 高 —— "秒回"是机器人特征 |
| **24 小时不间断在线** | 无头 Linux 服务器，7×24 | 🟡 中 —— 单看不算异常，叠加就明显 |
| **深夜活跃** | 凌晨 1 点还在高频答 | 🟡 中 |
| **主动发言** | 每小时最多 10 次插嘴 | 🟡 中 |

### 我的结论

> **根因是「行为模式」，不是「账号本身」。**
> 104 份 PDF/天 + 211 次秒回 —— 这两条叠加，在腾讯眼里就是标准的"非人类账号"。
> **换新号解决不了问题** —— 同样的行为，新号死得更快（新号风控更严）。

## 三、处置措施

### ① 立刻申诉（已完成 ✅）

腾讯对**首次冻结**通常给自助申诉通道，走 QQ 安全中心 → 申诉 → 人脸/短信验证。

### ② 扫码重新登录（已完成 ✅）

**⚠️ 重要认知**：申诉成功 ≠ 恢复登录。
申诉只是解冻账号，**登录态仍需重新扫二维码**（NapCat 会自动生成，2 分钟刷新一次）。

**取码方式**（已做成一键脚本）：
```bash
bash /home/qqbot/qq-bot/get_qr.sh
```
输出的二维码用**该账号所在的手机**扫。

### ③ 开启静默休息模式（已完成 ✅）

新增 `REST_MODE` 开关：

```bash
REST_MODE=1   # 零发送
```

**做什么**：
- ❌ 收到任何消息都不回（一个字都不发）
- ❌ 每日讲义、政治推送、日报 全部暂停
- ✅ **QQ 连接保持**（不登出、不重连）

**⚠️ 为什么"保持在线"比"登出"安全**：
```
✅ 在线但不说话  → 看着就是"挂着不说话的普通用户"，100% 正常
❌ 登出 QQ       → 反复登出/登录本身就是风控信号，反而更危险
```

**验证结果**：
```
REST_MODE = True
测试 @ 它 → 发出去的消息数 = 0   ✅
QQ 状态  → online: True          ✅
```

### ④ 多设备配置确认（已完成 ✅）

**当前设备配置（车主确认）**：
- **备用手機**：登录该号，**只挂着，不做任何操作**
- **主手机**：不登这个号
- **服务器**：登着（机器人）

**为什么这是最优配置**：

| 要点 | 说明 |
|---|---|
| **形态像真人** | 「手机 + 电脑同时在线」是 QQ 最标准的形态 |
| **无登录抖动** | ⚠️ 只有一台手机登 —— 避开"两台手机互挤下线"这个大坑（登录抖动是风控重点打击对象） |
| **有安全锚点** | 手机在，验证/申诉能第一时间响应 |
| **手机无额外行为** | 只挂着不说话，最干净 |

**备用手機维护要点**：
1. ⚠️ **关闭省电优化/后台清理** —— 否则 QQ 被杀 → 掉线 → 被迫重登（重登是风险）
2. 长期插电 + 连 WiFi
3. **不要在上面登出/登录**
4. 这几天不要更新 QQ 版本
5. 保证能收到验证短信/通知

## 五、这次暴露出的系统性问题

### ⚠️ 问题一：告警通道和执行通道是同一个（死循环）

```
healthcheck.sh 每 5 分钟检测一次
    ↓ 检测到 "OneBot 接口不通或未登录"
    ↓ 但告警方式 = 通过 OneBot 发 QQ 消息
    ↓ OneBot 正好坏了
    → 告警发不出去 → 只能靠人工发现
```

**这次是车主自己发现的，不是系统告警的** ❌

**改进方向**：加**独立告警通道**（邮件 / Server酱 / 短信），不依赖 QQ 本身。

### ⚠️ 问题二：没有"行为强度"的护栏

系统有能力限制**频率**（`MAX_CHAT_PER_HOUR`），但**没有限制"文件发送总量"** ❌
104 份 PDF 一天，系统全程没有任何阻拦。

**改进方向**：`throttle.py` 已经补上（每日 PDF 上限 + 每小时发送上限 + 随机间隔）。

### ⚠️ 问题三：对"冻结"这个状态没有区分

系统把"登录掉线"和"账号被冻结"当成同一件事处理 ——
**但两者的处置完全不同**：
- 掉线 → 自动重连即可
- 冻结 → **必须人工申诉**，且**继续重试登录可能加重问题**

**改进方向**：识别 NapCat 的 `ErrCode: 3` + "生成二维码"组合，直接**告警并暂停重试**。

## 六、给未来的自己的提醒

1. **QQ 个人号做机器人，天然有风控风险** —— 这不是"会不会"的问题，是"什么时候"
2. **文件传输是最高危行为** —— 能用图片就别用文件
3. **"秒回"是机器人特征** —— 加随机延迟不是体验问题，是安全问题
4. **账号要养，行为要像人** —— 手机+电脑同时在线、有停顿、有作息
5. **告警通道必须独立于被监控的系统** —— 否则等于没有告警

## 二、代码 bug：静默模式下仍然发了消息

### 现象

```
二号日志 07:00:19：群<群号> 冷场 260 分钟，发个表情包活跃一下：sticker_01.jpg
```

**二号本该完全静默（`REST_MODE=1`），却往群里发了张表情包。**

### 根因

```python
# 我原来的做法：在各个调用点加守卫
def handle_message(...):
    if config.REST_MODE: return          # ← 这里加了
    ...

def loop_group(...):
    handle_message(...)                   # 走守卫 ✅
    maybe_cold_sticker(group_id, ...)     # ← 绕过了守卫 ❌
```

**「冷场表情包」走的是另一条路径，压根不经过 `handle_message`。**

### 修法（重点）

**没有在漏掉的那个调用点补一个守卫，而是把守卫挪到最底层出口：**

```python
# onebot.py —— 所有发送的唯一出口
def _send(kind, target_id, message):
    throttle.note(...)            # 记账
    return call("send_group_msg", ...)

def send_group_text(...):
    if _throttle_blocked("msg"):  return None   # 节流闸
    if _rest_blocked("群文字"):    return None   # 静默闸
    return _send(...)
```

**9 个发送函数（群文字/@/图片/视频/文件 + 私聊文字/图片/视频/文件）全部加上。**

### 顺带发现的同类问题

**节流模块（`throttle.py`）犯了完全一样的错** —— 只挂在 `send_parts` 上，
其它路径绕过去就不计数、不限额。**同样挪到最底层出口。**

### 实测

```
每小时限额 3 条 → 第 4、5 条被拦 ✅
PDF 走同一套配额 ✅
静默模式 → 群文字/群图片/私聊 全拦 ✅
重试计数 199 → 199（30 秒没动）✅
```

### 教训（这条是今天最值钱的）

> **守卫和限额必须放在"最底层的出口"，不能放在各个调用点。**
>
> 调用点会漏 —— 因为**新的调用点随时会被加进来**（这次就是"冷场表情包"），
> 而出口只有一个，放对了就永远不会漏。
>
> 同一个错误我在这一个项目里犯了**两次**（守卫一次、节流一次），
> 都是"觉得放在主要路径上就够了"。**能放在出口，就别放在路上。**
